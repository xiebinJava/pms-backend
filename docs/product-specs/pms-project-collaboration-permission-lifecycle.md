# PMS 项目协作权限与生命周期规范

**版本**：v1.6
**状态**：已确认
**适用范围**：项目详情、项目流程、节点详情、节点任务看板、项目协作区及其前后端接口

## 1. 规范目标

本规范统一项目管理中的角色、权限、状态和数据锁定规则，作为前端展示、交互控制、后端接口鉴权和后续功能扩展的共同依据。

核心原则：

1. 项目读取对所有持有 `project:read` 的员工开放，项目、节点、任务分别控制写入边界。
2. 后端权限校验是最终依据，前端隐藏或禁用控件只是交互层表现。
3. 项目创建人和项目经理拥有项目级完整权限，但不能绕过项目状态和已完成节点的只读规则；具体操作仍受生命周期状态约束。
4. 已完成节点必须先回滚为“进行中”，才能再次编辑。
5. 终止是生命周期状态，不等同于删除，数据和操作记录必须保留。
6. 系统管理员是独立于项目成员角色的全局权限组，对所有项目拥有完整操作权限，但仍遵循已完成节点、已终止节点和已删除项目的生命周期只读约束。
7. 所有标准角色都可以创建项目；创建时不填写项目经理，第一个节点确认时再单独选择。项目创建人和项目经理拥有相同的项目级责任权限。
8. 项目等级参考企业《项目管理体系》中的战略（S）、关键（A）、重要（B）、常规（C）四档；优先级表示紧急程度，项目等级表示重要性，两者独立维护。

项目等级规则：

| 等级 | 编码 | 业务含义 | 系统行为 |
| --- | --- | --- | --- |
| 战略项目 | S / 3 | 集团或公司最高层重点关注，直接影响战略 | 记录等级，不自动替代企业审批流程 |
| 关键项目 | A / 2 | 跨部门，影响业务线核心指标 | 记录等级，不自动改变权限 |
| 重要项目 | B / 1 | 部门级重点，影响有限范围 | 记录等级，不自动改变权限 |
| 常规项目 | C / 0 | 日常改进或小型项目 | 新建项目默认值 |

项目等级在启动节点的项目基本信息中维护，创建时不要求填写项目经理。等级评估可参考投资规模、项目复杂度、战略重要性和项目收益；本系统当前只保存和展示等级，不把等级直接推导为审批人、权限或自动流程。

## 2. 角色与数据归属

| 角色 | 权威字段 | 定义 |
| --- | --- | --- |
| 项目创建人 | `project.createdBy` | 创建项目的用户，创建后不可因项目经理变更而改变 |
| 项目经理 | `project.projectManagerId` | 第一个节点完成确认后，对项目整体结果负责的用户；未确认时为空 |
| 节点负责人 | `project_node.ownerId` | 由项目经理或项目创建人分配，负责指定节点 |
| 任务负责人 | `project_task.assigneeId` | 负责执行指定任务的用户 |
| 项目成员 | 项目成员关系 | 项目协作范围内的参与者 |
| 关注人 | 项目关注关系 | 接收项目动态的用户，默认不具备编辑权限 |
| 系统管理员 | `sys_user.systemRole` | 全局权限组，不依赖项目成员关系即可管理所有项目 |

项目创建人和项目经理的项目级权限相同，但业务身份不同，前端必须分别展示。项目经理未确认时，项目头部显示“待确认”。

现有成员角色字段可继续用于成员关系和展示，但不能单独作为上述业务权限的唯一依据。业务权限应以项目创建人、项目经理、节点负责人和任务负责人字段为准。

## 3. 项目状态

项目状态统一为以下四种，前后端、列表筛选、详情页和统计接口必须使用同一组状态码与文案。节点仍单独使用“未开始、进行中、已完成、已终止”四种状态。项目列表当前不展示概览统计卡片，后续企业级项目概览重构时再接入统计接口。

| 状态 | 含义 | 进入条件 |
| --- | --- | --- |
| 进行中 | 项目正在推进 | 项目启动后进入；恢复项目后重新进入 |
| 已完成 | 项目全部节点完成 | 所有节点状态均为“已完成”时自动进入 |
| 已终止 | 项目被主动终止 | 项目创建人、项目经理或具备项目治理权限的角色主动终止 |
| 已删除 | 项目被逻辑删除 | 项目创建人、项目经理或具备项目治理权限的角色删除项目 |

项目状态流转：

```text
进行中 ──所有节点完成──> 已完成
进行中 ──终止项目────> 已终止
进行中 ──删除项目────> 已删除
已完成 ──回滚节点────> 进行中
已终止 ──恢复项目────> 进行中
```

约束：

- 不通过删除项目实现终止。
- “已删除”采用逻辑删除，项目记录、节点、任务、成员、里程碑和动态保留用于只读查看与审计。
- 项目创建后自动进入“进行中”，并自动将第一个节点设置为“进行中”；只有“进行中”项目可以执行终止操作。
- 历史数据中的项目状态 0 视为“进行中”，不得在界面作为“未开始”展示。
- “已完成”“已终止”和“已删除”项目不可写入；已终止/已删除项目只能由项目创建人、项目经理或具备项目治理权限的角色恢复。已删除项目对普通读取视为不存在，不出现在列表、搜索、统计或普通直链中。
- 已终止项目保留终止前的节点、任务、成员和动态数据。
- 已终止项目恢复后，从被终止节点继续推进。
- 已完成项目如需继续处理，必须先回滚节点。
- 项目进度按节点计算：`已完成节点数 / 节点总数 × 100%`。
- 终止时保留终止前进度；页面可展示“已终止 · xx%”。

## 4. 节点状态与流转

节点状态为：未开始、进行中、已完成、已终止。

```text
未开始 ──启动节点──> 进行中
进行中 ──完成节点──> 已完成
进行中 ──终止项目──> 已终止
已完成 ──回滚节点──> 进行中
已终止 ──恢复项目──> 进行中
```

项目在某个节点终止时：

- 之前已经完成的节点保持“已完成”；
- 当前进行中的节点变为“已终止”；
- 后续节点保持“未开始”；
- 项目状态变为“已终止”。

节点状态颜色全局统一：

| 状态 | 颜色语义 |
| --- | --- |
| 未开始 | 灰色 |
| 进行中 | 橙色 |
| 已完成 | 绿色 |
| 已终止 | 红色 |
| 已删除 | 红色 |

项目状态、节点流程节点、节点详情状态、任务相关状态标签应遵循同一套语义，不再按页面单独定义颜色。项目状态使用“进行中”橙色、“已完成”绿色、“已终止/已删除”红色；历史项目状态 0 按“进行中”展示。

## 5. 已完成节点锁定规则

已完成节点的页面进入严格只读状态，任何角色都不能直接修改。已终止节点和已删除项目下的页面同样只读。

锁定范围包括：

- 节点说明和节点业务字段；
- 节点负责人；
- 交付物和节点附件；
- 节点任务看板；
- 任务标题、描述、交付物、负责人、优先级、截止日期和状态；
- 节点相关的可编辑记录。

只有项目创建人或项目经理可以回滚已完成节点。回滚时：

1. 目标节点从“已完成”变为“进行中”；
2. 目标节点之后的节点变为“未开始”；
3. 项目状态变为“进行中”；
4. 目标节点重新允许节点负责人编辑；
5. 回滚必须记录操作人、操作时间、目标节点和回滚原因。

已终止节点同样不能直接编辑，必须先恢复项目，使该节点变为“进行中”。系统生成的审计记录不可修改或删除。

## 6. 权限矩阵

权限判断先经过功能权限，再结合数据范围或项目责任关系。读取不是“参加项目才可见”：所有已登录且持有 `project:read` 的员工都可以查看全公司项目及其任务、节点、里程碑、评论、附件、成员和关注人。反馈中心有独立的 `feedback:*` 权限，不继承项目读取。

### 6.1 内置角色矩阵

| 角色 | `project:read` | `project:create` | 常规 `project:write` | `project:manage` | `project:comment:write` |
| --- | --- | --- | --- | --- | --- |
| `member` | 全公司 | 本人当前有效主归属组织 | 无角色级常规写；本人任务/节点有限写 | 无角色级治理；责任项目可按责任路径操作 | 全公司项目 |
| `project_manager` | 全公司 | 本人当前有效主归属组织 | 自己创建或担任项目经理的项目；其他项目按责任关系 | 仅自己创建或担任项目经理的项目 | 全公司项目 |
| `project_admin` | 全公司 | 全公司 | 全公司 | 全公司 | 全公司项目 |
| `org_admin` | 全公司 | 本人组织及下级 | 本人组织及下级 | 本人组织及下级 | 全公司项目 |
| `dept_manager` / `business_owner` | 全公司 | 本人组织及下级 | 本人组织及下级 | 第一期不授予角色级治理 | 全公司项目 |
| `system_role = 1` | 全局绕过 | 全局绕过 | 全局绕过 | 全局绕过 | 全局绕过 |

`SELF` 对项目创建的含义是“本人当前有效主归属组织”，不包含下级组织；其他 `SELF` 读取/写入语义仍按对应资源的责任关系解析。多个角色取权限并集。

### 6.2 项目关系矩阵

| 操作 | 系统管理员 | 创建人/项目经理 | 节点负责人 | 任务负责人 | 项目成员/关注人 |
| --- | --- | --- | --- | --- | --- |
| 查看项目及全部内容 | 全部 | 全部 | 全部 | 全部 | 全部（需 `project:read`） |
| 编辑项目资料 | 全部 | ✓ | — | — | — |
| 管理项目成员、关注人和项目经理 | 全部 | ✓ | — | — | — |
| 分配节点负责人 | 全部 | ✓ | — | — | — |
| 编辑未开始/进行中节点 | 全部 | ✓ | 负责节点的有限内容 | — | — |
| 编辑已完成节点 | 先回滚 | 先回滚 | 先回滚 | 先回滚 | 先回滚 |
| 编辑已终止节点 | 先恢复 | 先恢复 | 先恢复 | 先恢复 | 先恢复 |
| 管理节点任务结构 | 全部 | ✓ | 负责节点内 | — | — |
| 修改自己的任务内容和附件 | 全部 | ✓ | 负责节点内 | 自己的任务 | — |
| 修改他人任务、移动或删除任务 | 全部 | ✓ | 负责节点内 | — | — |
| 完成节点 | 全部 | ✓ | 负责节点 | — | — |
| 回滚节点 | ✓ | ✓ | — | — | — |
| 终止项目 | ✓ | ✓ | — | — | — |
| 恢复项目 | ✓ | ✓ | — | — | — |
| 管理里程碑 | ✓ | ✓ | — | — | — |
| 查看和发布项目动态 | ✓ | ✓ | ✓ | ✓ | ✓（需评论权限） |

同一用户同时具备多个角色时，权限取各角色权限的并集。系统管理员的全局权限不依赖项目成员关系和具体业务角色。

## 7. 任务权限边界

任务负责人即使没有 `project:write`，也可以在项目处于进行中且节点可写时修改自己任务的：

- 标题；
- 描述；
- 交付物；
- 状态；
- 截止日期；
- 执行说明和附件。

任务负责人可以由项目成员中的节点负责人、项目经理或项目创建人担任，也可以是其他被纳入项目协作范围的成员。同一用户同时承担项目经理、节点负责人或项目创建人等角色时，权限按角色并集计算；例如项目经理将任务分配给自己后，仍保留项目经理的全部权限。

任务负责人不能修改任务负责人、所属节点、里程碑归属、移动任务或删除其他任务。任务优先级、负责人、节点归属和里程碑归属由项目创建人、项目经理、具备治理权限的角色或对应节点负责人调整。

任务看板属于节点详情的一部分，随节点切换展示不同任务。已完成或已终止节点下的任务全部只读。

### 7.1 子任务

子任务最多一层，必须和父任务属于同一个项目节点。子任务状态支持待办、进行中和已完成；截止日期可选，未填写时不单独生成临期/逾期提醒。已完成父任务不能新增子任务。父任务通过编辑或看板移动变为已完成时，服务端事务会同步完成所有直接子任务，并仅为原本没有截止日期的子任务补写父任务完成当天日期，已有日期不覆盖。父任务完成后不允许直接把子任务改回未完成，必须先回退父任务。删除子任务沿用任务删除能力和危险操作确认。

## 8. 项目协作区

项目协作区属于公共区域，不按节点复制，保留以下内容：

- 里程碑；
- 成员；
- 动态。

节点任务看板不属于公共协作区，必须放在对应节点详情页中。公共协作区遵循项目级权限和各自资源的操作规则。

## 9. 前后端实现约束

### 9.1 后端

新增统一的项目权限服务，至少提供以下判断：

```text
canCreateProject()
canReadProject(projectId)
canManageProject()
canManageMembers()
canSetProjectManager()
canManageNode(nodeId)
canEditNode(nodeId)
canCompleteNode(nodeId)
canRollbackNode(nodeId)
canManageTask(taskId)
canEditOwnTask(taskId)
canWriteComment(projectId)
canTerminateProject(projectId)
canRestoreProject(projectId)
```

所有新增、编辑、删除、任务移动、节点完成、节点回滚、项目终止和项目恢复接口都必须在服务层进行权限校验。无权限统一返回明确的禁止访问结果，不允许仅依赖前端按钮隐藏。

项目详情接口应返回当前项目内当前用户的能力集合；`canCreateProject` 是登录态或项目列表级能力，不挂在单个项目详情上。例如：

```json
{
  "permissions": {
    "canManageProject": false,
    "canManageMembers": false,
    "canSetProjectManager": false,
    "canAssignNodeOwner": false,
    "canTerminateProject": false,
    "canRestoreProject": false,
    "canDeleteProject": false,
    "canWriteComment": true
  }
}
```

节点 DTO 另行返回 `canEdit`、`canManageTasks`、`canComplete`、`canRollback` 和 `readOnly`；任务 DTO 另行返回 `canEdit`、`canMove`、`canDelete` 和 `readOnly`。前端按钮只消费这些后端能力字段，不在组件内自行推导管理权限。

### 9.2 前端

- 根据 `permissions` 控制按钮、输入框、下拉框和任务操作菜单；
- 已完成、已终止节点统一渲染为只读控件；
- 回滚按钮仅在当前节点为“已完成”且当前用户有回滚权限时展示；
- 终止、恢复、回滚等高风险操作必须二次确认；
- 无权限操作不只隐藏，也应在数据状态上阻止本地修改提交；
- 页面状态颜色统一复用状态令牌，不在组件内单独写颜色。

## 10. 审计与异常处理

以下操作必须记录审计日志，并与成功业务变更在同一事务内提交：

- 项目经理变更；
- 节点负责人变更；
- 节点完成；
- 节点回滚；
- 项目终止和恢复；
- 任务负责人、优先级、状态和归属变更；
- 项目资料和节点关键字段修改。
- 任务创建、编辑、移动、删除以及负责人、优先级、状态、节点和里程碑变化；
- 成员增删/角色变更、关注人替换、评论增删、任务附件和项目图片上传/删除；
- 角色创建/删除、权限点和数据范围变化、员工角色/归属/状态变化、组织变化、导入提交、密码重置和账号邀请激活。

审计记录至少包含：操作人、资源类型、资源 ID、项目 ID（项目域）、动作编码、白名单变更前后摘要、结果、请求 ID、UTC 操作时间、IP、User-Agent 和操作原因（适用时）。审计读取只要求 `admin:audit:read`，不继承 `project:read`；普通 GET 不记录。评论/反馈正文、令牌、密码、来源 URL、幂等键和附件二进制不得进入审计。

动作编码必须稳定，权限变更至少拆分为 `ROLE_PERMISSION_CHANGED`、`ROLE_SCOPE_CHANGED`、`USER_ROLE_ASSIGNED`、`USER_ROLE_UNASSIGNED`；项目经理变更使用 `PROJECT_MANAGER_CHANGED`，不能藏在普通项目资料更新中。审计页支持按动作、资源、项目、操作人、结果、请求 ID、时间和分页查询，详情按字段显示 before/after 差异。默认保留期 180 天，清理按批次执行并记录 `AUDIT_RETENTION_RUN`。

## 11. 验收标准

1. 项目创建人和项目经理可以执行项目级全部操作。
2. 项目经理为空时，页面显示“待确认”。
3. 节点负责人只能编辑自己负责的节点。
4. 任务负责人只能修改自己的任务。
5. 已完成节点所有页面内容均为只读。
6. 已完成节点只能通过回滚恢复为可编辑状态。
7. 项目终止时当前节点变为“已终止”，后续节点保持“未开始”。
8. 项目完成、终止、恢复、回滚和逻辑删除后的状态在前后端保持一致；历史项目状态 0 按进行中兼容。
9. 未授权接口调用返回禁止访问，不能通过绕过前端直接修改数据。
10. 项目创建后自动为进行中，项目列表可以筛选进行中、已完成、已终止、已删除四种状态；统计接口按同一组四态返回，当前列表页暂不展示概览统计卡片。
11. 所有项目状态和节点状态使用统一颜色和文案。

## 12. 实施顺序

1. 统一项目创建人、项目经理、节点负责人和任务负责人的字段语义。
2. 统一项目状态、节点状态及状态流转规则。
3. 后端实现集中式权限判断和接口拦截。
4. 后端返回当前用户能力集合。
5. 前端接入能力集合，实现按钮和表单状态控制。
6. 实现已完成节点只读和回滚解锁流程。
7. 实现项目终止、恢复及审计记录。
8. 为不同角色、不同状态补充接口测试和页面交互测试。
