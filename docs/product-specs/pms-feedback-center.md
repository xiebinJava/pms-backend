# PMS 反馈中心设计

## 1. 目标与边界

反馈中心用于收集企业内部用户在 PMS 中遇到的问题、改进建议和使用疑问，并形成可追踪的处理闭环。它与项目评论是两套不同能力：评论用于项目协作上下文中的讨论；反馈中心用于跨项目的问题受理、分诊、分派、处理和审计。

V1 只允许已登录的企业用户提交反馈，不开放匿名或外部访客入口。反馈可以关联项目、任务或节点，但没有业务上下文的系统问题也可以直接提交。

## 2. 角色与职责

| 角色 | 能力 |
| --- | --- |
| 普通员工 | 提交反馈；查看自己提交的反馈及处理进度；查看自己的处理记录；对已解决反馈重新打开 |
| 反馈管理员 | 按 `feedback:manage` 的数据范围查看反馈；分诊和分派；调整优先级；填写处理说明；标记解决/关闭；处理重复、无法复现和拒绝。只有全公司数据范围才可查看全部反馈 |
| 超级管理员 | 拥有反馈管理员全部能力，并负责权限和运维审计 |

`feedback:read` 控制用户反馈入口和本人数据读取，`feedback:write` 控制提交和本人反馈重开，`feedback:manage` 控制按授权范围的列表、分诊、分派和关闭。反馈权限按模块内层级继承：`feedback:manage` 同时满足读和写，`feedback:write` 同时满足读；其他权限族仍保持精确匹配。内置组织管理员和超级管理员默认拥有管理权限；所有内置角色默认可提交和查看自己的反馈。

## 3. 反馈类型与优先级

类型：

- `QUESTION`：使用疑问或规则澄清。
- `BUG`：功能错误、接口错误或数据错误。
- `FEATURE`：新功能或流程改进建议。
- `UX`：交互、视觉、可访问性或响应式问题。
- `DATA`：数据质量、导入、归属或统计问题。
- `PERMISSION`：权限、组织范围或账号问题。
- `OTHER`：暂时无法归入上述类别的反馈。

优先级：`LOW`、`NORMAL`、`HIGH`、`URGENT`。提交人可以建议优先级，反馈管理员在分诊时可以调整。优先级不是 SLA 承诺，生产环境应由企业运维策略另行定义响应时限。

## 4. 状态机

主流程：

```text
提交反馈 → 待初步处理 → 已分派 → 处理中 → 待确认 → 已解决 → 已关闭
```

异常状态：`已拒绝`、`重复反馈`、`无法复现`。异常状态只能由反馈管理员设置，并必须留下处理说明。

允许的状态变化：

- `PENDING_TRIAGE` → `ASSIGNED`、`REJECTED`、`DUPLICATE`、`UNREPRODUCIBLE`
- `ASSIGNED` → `IN_PROGRESS`、`REJECTED`、`DUPLICATE`、`UNREPRODUCIBLE`
- `IN_PROGRESS` → `PENDING_CONFIRMATION`、`REJECTED`、`DUPLICATE`、`UNREPRODUCIBLE`
- `PENDING_CONFIRMATION` → `RESOLVED`、`IN_PROGRESS`
- `RESOLVED` → `CLOSED`、`IN_PROGRESS`
- `CLOSED` → `IN_PROGRESS`（重新打开）
- 异常状态 → `IN_PROGRESS`（管理员重新受理）

“分诊”在页面上使用“待初步处理”文案，表示管理员确认反馈类型、优先级、关联范围、重复关系和处理人；它不是用户需要理解的技术术语。

## 5. 数据与一致性

核心表：

- `feedback_ticket`：当前反馈快照、提交人、上下文、处理人、状态、版本和幂等键。
- `feedback_history`：只追加的状态/分派/优先级/说明变更历史。

可见性与约束：

- 普通员工只能读取自己提交的工单；具备 `feedback:manage` 的处理人员按其组织/自定义/项目数据范围查看和处理，只有 `ALL` 范围可查看全量；提交人始终可以查看自己的工单。
- 反馈管理员通过反馈专用负责人选项接口获取候选人，候选人只包含启用且处于当前管理数据范围内的用户；不要求额外的人员管理读权限。

- `ticket_no` 唯一且按 `FB-YYYYMMDD-XXXX` 生成。
- `client_request_id` 与提交人组成唯一键，重复提交返回已有工单，不重复创建。
- `version` 用于乐观锁；更新携带旧版本，冲突返回 409。
- `closed_at` 仅在首次进入“已关闭”时写入；离开“已关闭”时清空，重复保存已关闭工单不会刷新关闭时间；重开未填写新说明时清空旧处理说明。
- 反馈、历史和上下文外键必须指向现存记录；软删除不删除审计历史。
- 标题、正文、处理说明限制长度；所有写操作写入 `sys_operation_log`，不得记录密码、Token 或完整认证头。
- 操作审计只记录工单号、类型、状态、优先级、关联 ID、人员 ID、关闭时间、版本和“是否有处理说明”等白名单字段，不记录标题、正文、来源 URL、幂等键或处理说明原文。

## 6. API 契约

- `POST /feedback/tickets`：创建反馈。
- `GET /feedback/tickets`：按本人/管理员范围分页查询，支持关键词、类型、状态、优先级。
- `GET /feedback/tickets/assignees`：按反馈管理数据范围返回可分派的启用用户。
- `GET /feedback/tickets/{id}`：查看反馈详情和历史。
- `PATCH /feedback/tickets/{id}`：管理员更新状态、优先级、处理人和处理说明；必须携带 `version`。
- `POST /feedback/tickets/{id}/reopen`：提交人或管理员重新打开已解决/已关闭/异常反馈。

所有接口遵循 PMS 的统一 `ResponseResult`、401/403/409/422 错误语义和 `X-Request-Id` 链路标识。

## 7. 页面交互

反馈中心放在左侧导航底部，采用与现有 PMS 一致的页面头、筛选栏、表格、抽屉和状态标签。普通员工看到“我的反馈”和“提交反馈”；反馈管理员看到“全部反馈”、处理筛选和详情抽屉中的分诊/分派控件。提交成功后展示工单号，详情中展示上下文、当前状态和时间线。

附件、评论线程、重复关联、转任务、通知和 SLA 统计属于后续增量；V1 先保证核心受理闭环和审计可追溯。
