# 项目权限与数据范围收口设计

## 1. 目标

将项目域的“查看”和“操作”规则统一为可测试、可解释、不会因角色级数据范围误伤业务责任人的权限模型：所有持有 `project:read` 的标准员工可查看所有未删除项目及其项目内容；创建项目对所有标准员工开放；常规写入、项目治理、任务负责人有限写入和项目生命周期分别按功能权限、组织范围或项目责任关系控制。

## 2. 已确认的业务决策

### 2.1 项目读取

- 读取前提是用户已登录且持有 `project:read`，不是“只要登录就可读”。
- `project:read` 在项目域固定覆盖为 `ALL`；不受角色页面中的角色级 `SELF` 范围影响，也不开放给角色管理页面修改。
- 可读内容包括项目、任务、节点、里程碑、评论、附件、成员和关注人。
- 反馈工单使用自己的 `feedback:*` 和可见性规则，不继承 `project:read`。
- `DELETED` 项目不进入普通列表、搜索、统计或普通详情；直链按不存在处理，不暴露项目仍存在。
- `TERMINATED` 项目可读，但项目资料、任务、节点、附件、评论和其他写操作均不可用；只有恢复是生命周期例外。
- 工作台仍是个人待办和个人参与上下文，不因项目全员可读而展示公司全部项目。
- `system_role = 1` 保留现有管理员绕过，但不作为普通员工验收用例。

### 2.2 项目创建

- 所有标准员工角色默认拥有 `project:create`。
- 创建项目不要求项目经理；项目经理在第一个节点确认时单独选择。
- 创建人写入 `created_by`，并自动加入项目成员；创建人和项目经理最终拥有完全相同的项目级责任权限。
- `SELF` 创建范围指用户当前有效的主属组织本身，不包含下级组织；没有有效主属组织时拒绝创建。
- `ORG_AND_DESCENDANTS` 可选择本组织及下级；`ALL` 可选择全公司有效组织。
- 创建权限不等于全局 `project:write` 或全公司 `project:manage`。

### 2.3 项目写入与治理

项目写入分为两条授权路径，不能统一做“功能权限 + 数据范围 + 责任关系”的交集：

1. 治理路径：功能权限 + 角色数据范围。适用于 `ORG_ADMIN`、`PROJECT_ADMIN`、`DEPT_MANAGER`、`BUSINESS_OWNER` 和系统管理员。
2. 责任路径：功能权限（若该操作需要）+ 当前项目责任关系。适用于创建人、项目经理、节点负责人和任务负责人。

角色矩阵：

| 角色 | `project:read` | `project:create` | `project:write` | `project:manage` | `project:comment:write` |
| --- | --- | --- | --- | --- | --- |
| `MEMBER` | `ALL` | 主属组织 | 无全局权限；本人负责的任务/节点走有限责任写入 | 无全局权限；自己创建的项目走责任路径 | `ALL` |
| `PROJECT_MANAGER` | `ALL` | 主属组织 | 项目责任路径 | 自己创建或担任项目经理的项目 | `ALL` |
| `PROJECT_ADMIN` | `ALL` | `ALL` | 全公司治理 | 全公司治理 | `ALL` |
| `ORG_ADMIN` | `ALL` | 本组织及下级 | 本组织及下级治理 | 本组织及下级治理 | `ALL` |
| `DEPT_MANAGER` / `BUSINESS_OWNER` | `ALL` | 本组织及下级 | 本组织及下级治理 | 本期不开放 | `ALL` |
| `SUPER_ADMIN` | 全局绕过 | 全局绕过 | 全局绕过 | 全局绕过 | 全局绕过 |

- `PROJECT_ADMIN` 的全公司治理和 `ORG_ADMIN` 的组织范围治理是明确的权限行为，必须写入发布说明。
- `DEPT_MANAGER` / `BUSINESS_OWNER` 可在本组织及下级组织范围内创建和常规写入项目，但不新增项目生命周期和成员治理能力。
- 创建人和项目经理对自己的项目权限完全一致，包括资料、排期、节点、任务、成员、评论、终止、恢复和删除；该责任关系只作用于当前项目，不扩大到其他项目。
- 项目负责人 `ownerId` 不是权限来源；项目责任人只认创建人、项目经理、节点负责人和任务负责人。

### 2.4 任务、节点和评论有限写入

- `MEMBER` 不授予 `project:write`。
- 任务负责人可在项目和节点允许操作时修改自己的任务内容、状态、截止日期，并上传自己任务的附件；这些有限操作要求 `project:read` 和责任关系，不要求 `project:write`。
- 节点负责人可执行当前已有策略允许的节点有限操作，不要求 `project:write`；修改别人的节点或进行治理操作仍走治理/项目责任路径。
- 创建任务、修改别人的任务、任务移动/删除、节点负责人调整、节点排期和里程碑管理等常规治理写入要求 `project:write` 或对应项目责任路径。
- 项目评论读取继承 `project:read`；新增和删除自己的评论使用 `project:comment:write`，不要求 `project:write`。
- 第一阶段没有评论编辑接口，不设计作者编辑能力；治理角色可按项目管理权限删除他人评论。

## 3. 生命周期与查询边界

服务层应提供清晰的状态入口，而不是让一个方法隐式覆盖所有场景：

- `requireProjectReadable`：加载非删除项目；允许 `ACTIVE`、`COMPLETED`、`TERMINATED`；删除项目按不存在处理。
- `requireProjectOperational`：只允许 `ACTIVE` 项目进行常规写入、评论和附件变更。
- `requireProjectRestorable`：允许治理角色或当前项目责任人加载终止/软删除记录，并只执行恢复。
- `requireProjectDeletable`：只允许满足项目管理权限和当前状态的软删除操作。

项目列表、详情、搜索、统计和全部项目内容读取必须使用一致的非删除条件。`ALL` 项目读取不能先调用 `listReadableIds()` 把所有项目 ID 装入内存；搜索必须直接在项目、任务、里程碑和评论表上使用数据库条件及分页。

## 4. 附件和资源绑定

- 任务附件读取、下载、上传和删除必须通过任务所属项目进行校验。
- 项目图片读取不能只凭文件名和 `project:read`；上传返回的资源必须绑定项目 ID，读取时校验项目可读，写入时校验项目操作权限。
- 成员和关注人列表必须先校验项目可读；成员、关注人变更必须校验项目管理权限。
- 任何资源 ID 不匹配路径项目时返回不存在或明确业务错误，不能返回另一项目的数据。

## 5. 前端约定

- 项目入口和列表是否显示由用户级 `project:read` 与 `project:create` 决定。
- `canCreate` 是用户级能力，放在登录态或项目列表上下文，不放到单个项目 DTO。
- 项目 DTO 只返回项目级 capability；节点和任务 DTO 继续返回自己的 `canEdit`、`canMove`、`canDelete`、`readOnly` 等细粒度能力。
- 已终止/已删除项目的写入按钮由后端 capability 隐藏或禁用；前端不能用项目状态推断权限作为后端替代。
- 任务负责人应看到自己的有限任务写入入口；普通读者不能看到项目资料、成员、节点治理和任务管理入口。

## 6. 实施约束

- `DataScopeType` 继续使用现有 `SELF`、`SELF_AND_SUBORDINATES`、`ORG`、`ORG_AND_DESCENDANTS`、`CUSTOM_ORGS`、`ALL`；不新增平行枚举。
- `project:read -> ALL` 采用后端代码内固定策略，不作为角色管理页面可编辑的范围配置。
- 人员、组织、审计模块本期不修改现有权限码和过滤逻辑；项目全员可读不得扩大这些模块的权限。
- 任何接口级 `@RequirePermission` 调整都必须由服务层责任/状态/范围校验补足，前端按钮隐藏不能作为安全措施。

## 7. 验收标准

1. 有 `project:read` 的普通员工可以查看非本人、非成员的所有未删除项目。
2. 普通员工可以查看项目任务、节点、里程碑、评论、成员、关注人和附件。
3. 所有标准员工角色都可以创建项目；创建组织遵守各自范围；项目创建时没有项目经理字段。
4. 创建人和首节点确认后选定的项目经理拥有同等项目级操作和管理能力。
5. 普通员工不是任务负责人时不能写任务；是任务负责人时能写自己的有限任务内容和附件，但不能改项目资料或别人的任务。
6. 普通员工可以发布并删除自己的项目评论；不需要 `project:write`。
7. `ORG_ADMIN` 只能治理本组织及下级项目；`PROJECT_ADMIN` 可以治理全公司项目；项目经理可以操作自己负责的跨组织项目。
8. 已终止项目可读但不能新增评论或进行普通写操作，恢复是唯一例外。
9. 已删除项目普通读取按不存在处理，责任人或治理角色仍可进入恢复流程。
10. 搜索、统计、详情和列表一致；工作台仍然只展示个人相关内容。
11. 项目图片、成员、关注人、任务附件和直接 ID 访问不能绕过项目权限。
12. 人员、组织、审计权限码和现有行为本期保持不变。
