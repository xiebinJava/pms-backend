# 需求接收与分析组件设计

## 1. 背景与目标

需求录入节点负责把原始需求保存下来；需求接收节点负责判断这条需求是否值得进入后续交付流程，并形成可追溯的分析结论。该节点需要支持：

- 需求过滤：解释、澄清、检视，识别重复、无效、低价值或暂时无法判断的需求；
- 需求分析：区分功能需求与非功能需求，评估优先级、可实现性、ROI 与战略契合度；
- 明确接收结果：通过、待补充、驳回；
- 通过流程模板配置组件的显示位置、区块和必填规则；
- 新建或重新发布需求流程模板后，继续复用同一套业务校验和终态规则。

## 2. 设计边界

本次新增一个需求流程专用运行时组件：`requirement-receiving-analysis`（需求接收与分析）。它不是一组互相独立的普通自定义字段，而是一个拥有统一数据模型、校验和动作的业务组件。

现有需求字段绑定继续作为唯一事实来源：

- `requirement.title`：需求名称；
- `requirement.description`：需求描述；
- `requirement.owner`：需求负责人；
- `requirement.businessLine`：业务线；
- `requirement.priority`：最终优先级。

组件不得复制这些字段。组件只保存过滤、分析和接收决策数据；最终优先级继续写入现有需求优先级字段，保证需求列表、AI 接口和后续项目/专题/故事流程读取同一个值。

## 3. 详情页结构

节点详情沿用现有流程节点壳：节点负责人和节点排期固定显示在顶部，完成节点按钮仍位于右侧。业务组件建议按以下顺序展示：

### 3.1 需求概览

使用只读或按模板绑定的字段展示需求录入结果：名称、描述、负责人、业务线、当前优先级和当前执行对象。这里用于理解上下文，不新增重复编辑模型。

### 3.2 需求过滤

字段与行为：

- 有效性：待判断、有效、无效、信息不足；
- 过滤原因：重复需求、超出范围、信息不足、低价值、不可实现、已有方案、其他；
- 需求解释：把原始描述整理为清晰的问题、目标和预期结果；
- 过滤备注：补充依据、事实和待核查信息。

过滤原因支持多选；选择“其他”时必须填写备注。有效性和需求解释是完成需求接收前的核心信息。

### 3.3 需求分析

字段与行为：

- 需求分类：功能需求、非功能需求；
- 可实现性：1～5 分；
- ROI：1～5 分；
- 战略契合度：1～5 分；
- 综合价值分：由系统自动计算，不允许直接编辑；
- 价值结论：高、中、低，由综合分映射，同时允许分析人员填写说明。综合分为 4.0～5.0 时为高，2.5～3.9 时为中，1.0～2.4 时为低；
- 最终优先级：复用 `requirement.priority` 绑定，由现有单选控件编辑；
- 分析结论：说明评分依据、依赖条件和风险。

综合价值分采用三项评分的等权平均，保留一位小数；只有三项都有值时才计算综合分和高/中/低价值结论，评分不完整时显示“待评估”。评分项是结构化数据，分析结论是解释性文本；二者都要进入节点快照，便于审计和后续复盘。

### 3.4 接收结论

结论使用单选按钮：

- 通过：需求进入下一个流程节点；
- 待补充：需求仍停留在当前节点，允许保存补充信息，但不允许完成节点；
- 驳回：需求标记为无效并结束需求流程。

“待补充”必须填写补充说明，说明需要业务方补充的内容；“驳回”必须填写驳回原因。有效性和接收结论必须一致：有效性为“待判断”时不能完成节点；有效性为“无效”只能选择“驳回”；有效性为“信息不足”只能选择“待补充”；有效性为“有效”才能选择“通过”。驳回操作使用独立动作，不复用普通“完成节点”接口，避免线性流程错误地打开下一个节点。

## 4. 流程规则

### 4.1 保存规则

- 节点未开始或进行中时，组件可编辑，沿用当前节点权限和自动保存机制；
- 已完成节点只读；
- 组件数据必须随当前流程节点版本保存，模板发布后已有需求继续使用其绑定的流程快照；
- 所有写操作使用节点版本或需求版本校验，避免多人并发覆盖。
- 过滤和分析数据的保存权限沿用 `requirement:write`；驳回和重新开启属于流程终态管理，使用 `requirement:manage`。

### 4.2 完成节点规则

完成节点前，后端统一校验：

1. 节点负责人已填写；
2. 节点排期完整且开始日期不晚于结束日期；
3. 模板配置的必填字段已填写；
4. 需求过滤、分类、评分和分析结论满足组件配置的必填规则；
5. 接收结论必须为“通过”。

“待补充”不能通过完成校验；“驳回”只能通过独立驳回动作结束流程。

组件数据保存、普通节点更新、完成节点和驳回动作都必须在后端执行一致性校验，不能只依赖前端禁用按钮。

### 4.3 驳回与重新开启

驳回不删除需求，也不删除流程节点和分析记录。需求生命周期状态增加 `REJECTED`，需求列表可按该状态筛选，详情页显示“已驳回”。同时在 `pms_development_item_workflow` 增加可为空的工作流终止状态字段 `terminal_status`，驳回时设置为 `REJECTED`。工作流处于终止状态时，所有节点操作、组件写入和完成动作都被后端拒绝，不能因为当前节点仍为进行中而继续推进。

有权限的用户可以执行“重新开启”：

- 将需求状态恢复为 `ACTIVE`；
- 清除工作流的 `terminal_status`；
- 将驳回所在节点恢复为进行中，之前已完成节点保持完成，之后节点保持未开始；
- 将需求流程回到需求接收节点；
- 保留原有驳回记录；
- 重新开启原因必填并写入操作日志。

这样既能结束无效需求，又保留纠错和复审能力。

需求管理模板最多允许配置一个“需求接收与分析”组件。该组件所在节点就是需求接收节点；重新开启时按当前需求流程快照定位该节点，不按新模板重新计算位置。如果历史模板没有该组件，则只能恢复需求状态并由管理员手动处理流程，不自动猜测节点。

## 5. 流程模板配置

在需求管理模板的组件库中新增“需求接收与分析”，只允许需求管理流程使用。组件配置项包括：

- 过滤区是否显示；
- 分析区是否显示；
- 接收结论区是否显示；
- 需求分类是否必填；
- 可实现性、ROI、战略契合度是否显示及是否必填；
- 分析结论是否必填；
- 是否允许驳回。
- 组件在同一个模板中最多配置一次；模板发布校验发现重复配置时拒绝发布。

模板编辑器仍通过 `contentOrder` 控制字段区和组件的位置，并在节点定义中为组件保存版本化的 `componentConfigs`，结构按组件 key 隔离，例如 `componentConfigs.requirement-receiving-analysis`。组件配置只影响展示和必填策略，最终权限、状态转换和数据合法性由后端再次校验。

区块被关闭时，该区块的数据不参与必填校验；关闭的区块不能同时配置为必填。接收结论区始终需要保留，否则模板不能发布，因为需求接收节点必须有明确的流程结果。

老模板不自动插入该组件，保证历史流程快照不发生意外变化。新建模板可以从组件库添加；发布后的新版本对新建需求生效。

## 6. 数据与接口

组件数据沿用现有流程节点的 `fieldValuesJson` 存储通道，但使用保留命名空间保存，不能混入普通自定义字段。例如：

```json
{
  "__components": {
    "requirement-receiving-analysis": {
      "validity": "VALID",
      "filterReasons": ["LOW_VALUE"],
      "interpretation": "...",
      "supplementNote": null,
      "category": "FUNCTIONAL",
      "feasibilityScore": 4,
      "roiScore": 3,
      "strategicFitScore": 5,
      "analysisConclusion": "...",
      "decision": "PASS",
      "decisionReason": "..."
    }
  }
}
```

最终优先级不放在上述 JSON 中，而是复用需求主表的 `priority`。驳回状态写入需求主表的 `status`，同时写入审计日志；组件快照保存驳回原因和当时的分析结果。

建议新增或扩展以下后端能力：

- 获取/保存需求接收分析组件数据；
- 校验需求接收组件数据；
- 完成需求接收节点；
- 驳回需求并结束流程；
- 重新开启已驳回需求。

组件配置和组件数据需要分别校验：模板发布时校验配置结构，运行时校验评分、枚举、必填项和组件 key。接口应复用现有权限、版本冲突、审计和操作日志机制，不绕过节点权限直接修改需求状态。

组件数据保存接口必须携带流程节点 id 和节点版本，保存时只更新 `__components.requirement-receiving-analysis` 命名空间，并保留同一节点上的普通自定义字段。驳回和重新开启接口需要在一个事务中同时更新需求状态、工作流 `terminal_status`、相关节点状态和审计记录。

数据库迁移增加 `pms_development_item_workflow.terminal_status` 可空字段，并为已有数据保持空值；已有需求状态继续保持 `ACTIVE`，不做历史数据重判。

## 7. 兼容与错误处理

- 旧模板、旧需求节点没有组件数据时显示空状态，不报错；
- 组件配置缺失时，需求流程仍按原有流程渲染；
- 历史节点读取不到某个已删除的配置项时保留原始快照，不尝试用新模板补写；
- 评分值超出 1～5、结论与必填数据不一致、驳回原因为空时由后端拒绝；
- 版本冲突提示用户刷新，不覆盖他人修改；
- 驳回或重新开启失败时，需求状态和流程节点保持事务一致；
- 历史模板没有 `componentConfigs` 时使用组件默认配置；未知组件配置只作为不透明数据保留，不影响其他节点加载。
- 数据库迁移失败或终止状态写入失败时，驳回操作整体回滚，不能出现需求已驳回但工作流仍可推进的半完成状态。

## 8. 测试与验收标准

### 模板与前端

- 组件只出现在需求管理流程模板组件库；
- 组件可以加入、移除、调整位置并随模板发布；
- 各区块按配置显示，必填标记与校验一致；
- 需求字段绑定仍回显需求录入数据，最终优先级使用同一字段；
- 未开始/进行中可编辑，已完成只读；
- “待补充”不能完成，“通过”可以完成，“驳回”走独立动作。

### 后端

- 评分范围、枚举值、必填规则和状态转换有单元测试；
- 完成节点会校验负责人、排期和组件必填内容；
- 驳回会原子地更新需求状态、流程状态和审计记录；
- 重新开启会恢复需求并保留历史记录；
- 无效/信息不足/有效与驳回/待补充/通过之间的不一致组合会被拒绝；
- 模板发布会拒绝重复的需求接收组件，并能正确迁移 `terminal_status` 字段；
- 并发版本冲突不会覆盖已有数据。

### E2E

覆盖一条完整路径：需求录入 → 需求接收保存过滤与分析 → 待补充拦截 → 补充后通过 → 进入后续节点；另覆盖驳回 → 列表显示已驳回 → 重新开启 → 返回需求接收。

## 9. 非目标

- 本次不新增需求、项目、专题、故事之间的关联模型；
- 本次不改变需求执行对象“一条需求只能关联一个项目、专题或故事”的既有规则；
- 本次不实现自动拆分项目、专题、故事；
- 本次不引入复杂的并行审批或多分支工作流；先保持现有线性流程，并通过驳回终态补足需求接收闭环。
