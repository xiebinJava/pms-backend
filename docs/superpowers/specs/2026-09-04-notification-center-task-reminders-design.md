# 通知中心与任务临期/逾期提醒设计规格

## 1. 目标与范围

本次建设在现有站内通知链路上补齐两项能力：

1. 增加独立的“通知中心”页面，支持查看、筛选、分页和批量已读。
2. 每天扫描任务，为符合条件的任务负责人生成一次临期或逾期站内提醒。

本方案只扩展现有 `user_notification`、`NotificationService` 和顶部铃铛，不新建第二套消息系统。第一期只做站内通知，不发送邮件、飞书、企业微信或出站 Webhook，也不把工作台改成全公司任务看板。

## 2. 已确认的业务规则

### 2.1 临期与逾期定义

提醒日期以企业配置时区计算，默认使用 `Asia/Shanghai`；数据库时间仍按现有约定保存为 UTC。

| 类型 | 判定条件 |
| --- | --- |
| 临期 | `dueDate` 为今天至今天后第 7 个自然日（含首尾），任务状态不是 `DONE` |
| 逾期 | `dueDate` 早于今天，任务状态不是 `DONE` |

“7 天”是自然日，窗口明确为 `dueDate ∈ [today, today + N]`；默认 `N = 7`，所以包含 8 个日期，不按 24 小时滚动计算。任务没有截止日期时不提醒。

通知触发采用“只提醒新进入，不回填历史”的策略：

- 临期通知只在任务今天新进入临期窗口时触发，即 `dueDate = today + N`；任务在后续日期仍属于临期状态，但不会每天重复提醒。
- 逾期通知只在任务今天刚逾期时触发，即 `dueDate = today - 1`；更早的历史逾期不补发。
- 到期当天不发临期通知，只在进入窗口的外沿当天发一次；因此“临期”不是每天 09:00 重复提醒。
- 新建或改期时，只有新的 `dueDate` 恰好等于当天 `today + N` 才可能写入临期通知；改到窗口内部、改成今天或改成其他窗口日期都不补发。
- 重开任务不补发临期或逾期通知，除非重开当天恰好落在上述临期/逾期边界，且对应去重键尚未写过。
- 上线第一天也遵循上述触发条件，不扫描并补写所有历史逾期。因此首日提醒量是“今天进入临期窗口的任务数 + 今天刚逾期的任务数”，而不是全部历史欠账。
- 作业因停机错过触发日时不回填错过的提醒；恢复后只处理当天触发条件，避免一次性灌满未读数。

状态分类和通知触发是两个概念：通知中心展示的提醒类型仍按临期/逾期类型归类，但作业只在进入边界当天写入通知。

### 2.2 收件人和排除条件

- 只通知任务当前 `assigneeId`，不通知项目创建人、项目经理、节点负责人、项目成员或关注人。
- 没有负责人时不生成通知。
- 只扫描有效用户、未删除任务和处于 `ACTIVE` 状态的项目。
- 已完成项目、已终止项目、已删除项目下的任务均不生成新提醒；已删除项目对普通读取仍视为不存在。
- 完成任务后不再生成提醒。任务重新打开后不补发，只有重开当天恰好满足临期外沿或刚逾期边界，且对应去重键尚未写过时才生成提醒。
- 更换负责人时只给新的 `assigneeId` 生成后续提醒；旧负责人已有的通知不收回、不改已读状态。旧通知是否还能打开由项目当前读取权限和生命周期决定。
- 提醒不改变任务状态、不改变任务截止日期、不改变负责人，也不产生审计中的业务写操作记录。

### 2.3 幂等与截止日期变化

同一任务的临期通知按“任务 + 截止日期”去重；同一任务的逾期通知按“任务 + 当地日期”去重：

```text
TASK_DUE_SOON:{taskId}:{dueDate}
TASK_OVERDUE:{taskId}:{today}
```

因此：

- 同一天重复执行扫描不会重复生成同一条逾期通知。
- 同一截止日期的临期通知只生成一次，不会每天重复刷屏；由于只在进入窗口当天触发，错过进入日也不会在窗口后续日期补发。
- 修改任务截止日期后，新的截止日期拥有新的临期去重键，但只有修改当天新的 `dueDate` 恰好等于 `today + N` 时才会实际插入临期通知；旧通知保留为历史记录。
- 任务从临期进入逾期后，会生成一条新的逾期通知；这两条记录都保留。
- 同一任务每个企业当地日最多生成一条逾期通知，逾期去重键使用 `taskId + today`，不使用 `dueDate`。
- 并发执行两个扫描实例时，数据库唯一约束保证最终只保留一条相同提醒。

通知标题和正文使用纯文本，至少包含任务名称、项目名称、截止日期以及“临期/逾期”状态；不得把用户输入当作 HTML 渲染。

## 3. 后端设计

### 3.1 数据库迁移 V15

在 `user_notification` 增加可空字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `dedupe_key` | `VARCHAR(128)` | 提醒幂等键；历史通知为空，普通事件通知为空，新提醒必填 |

增加唯一索引：

```text
uk_user_notification_dedupe (user_id, type, dedupe_key)
```

现有普通通知的 `dedupe_key` 为 `NULL`，沿用数据库对多个 `NULL` 不互相冲突的语义；新提醒始终写入非空键。迁移必须保持现有通知记录、已读状态、软删除状态和版本字段不变。

提醒记录第一期只允许从未读变为已读，不执行软删除，因此唯一索引不把 `deleted` 作为复用去重键的手段；不得软删除提醒后再次插入相同的 `dedupe_key`。若未来需要清理通知，必须另行设计包含软删除语义的索引和归档策略。

`UserNotificationDO` 增加内部字段 `dedupeKey`，但 `UserNotificationDTO` 不向前端暴露该字段，避免把实现细节变成客户端协议。

### 3.2 提醒扫描

新增 `TaskReminderService` 和 `TaskReminderJob`：

- `TaskReminderJob` 只负责按配置时区取得当前日期并触发服务。
- `TaskReminderService` 负责查询候选任务、判定类型、组装文案和幂等写入。
- 提醒候选查询必须在数据库侧完成状态、日期、项目和负责人的过滤，并在过滤完成后分页/批处理；不能先取固定数量再由 Java `keepReadable` 丢弃，也不能先把全量任务或全量项目 ID 读入 JVM。
- 提醒候选 SQL 至少限制：项目 `ACTIVE`、任务未删除、任务状态非 `DONE`、截止日期非空、负责人非空、负责人用户有效，并排除已删除项目。提醒作业不是某个登录用户的列表查询，项目可读性由权限收口后的全员 `project:read` 规则保证；权限收口完成前，必须在写入前逐条校验负责人对项目可读，或暂缓启用作业。
- 通知中心分页、顶部预览和未读数是当前用户查询，必须在 SQL 中排除项目已删除或当前用户不可读的通知，再执行 `COUNT`、排序和分页；三者不能先取固定数量再在内存中 `keepReadable`。
- 作业启用前提是项目权限收口已经上线；在“全员持有 `project:read` 且项目读取范围覆盖全公司”的权限改造尚未上线时，发布清单必须阻止打开提醒开关，不得假设负责人可读取项目。第一期配置默认 `enabled: false`，权限验收通过后再显式打开。
- 每个候选提醒独立处理；单条重复键冲突不能让整批失败。其他数据库错误要记录任务日期、任务 ID 和 request/trace 上下文，并让作业失败可观测。
- 服务接受可注入的 `Clock` 或明确的日期参数，测试不依赖宿主机当前日期。

推荐的配置项及默认值：

```yaml
pms:
  notification:
    task-reminder:
      enabled: false
      cron: "0 0 9 * * *"
      zone: "Asia/Shanghai"
      due-soon-days: 7
```

`cron` 使用 Spring 六段表达式，默认每天当地 09:00 执行。`due-soon-days` 必须为 1–30 的整数，产品默认值为 7；配置错误或超出上限时应用启动失败或拒绝创建调度任务，不得静默改成全量扫描。默认 `enabled: false`，只有项目权限收口上线并通过发布验收后才允许打开。第一期不增加手动触发接口，测试和运维通过服务日志验证调度结果。

### 3.3 通知服务与权限

现有事件通知继续使用 `NotificationService`。新增提醒类型：

- `TASK_DUE_SOON`
- `TASK_OVERDUE`

提醒必须直接写入 `user_notification`，不得调用会自动发布出站 Webhook 的现有 `emit()` 事件通知路径；如果复用通知服务，必须提供明确的“仅站内”写入入口或关闭 Webhook 的参数。第一期提醒不发布 Webhook。

提醒通过现有通知列表、未读数、单条已读和全部已读能力展示；不增加新的权限码。通知中心和通知接口仍要求 `project:read`，并且只能读取当前登录用户自己的收件箱。项目可见性目标是“持有 `project:read` 后可读取全公司项目内容”，但该权限改造尚未上线前，不能把目标模型当成现行事实；提醒功能必须排在权限收口之后启用，或在扫描写入前校验负责人对项目可读。提醒收件人额外必须是该任务负责人。

现有通知查询若带有项目关联，必须在 SQL 的 `WHERE` 条件中排除项目已删除或当前用户不可读的记录，再执行 `COUNT`、排序和分页；不能先 `LIMIT` 80 条再在内存中 `keepReadable`。已删除项目的通知不出现在列表和未读数中，也不通过 403 暴露“项目还在”；已终止项目仍可读，历史通知可以打开，但不再生成新提醒。标记已读接口必须继续校验通知归属，用户不能通过猜 ID 修改他人的通知。

### 3.4 接口契约

保留现有接口，确保顶部铃铛兼容：

```text
GET  /notifications?unreadFirst=true&limit=20
GET  /notifications/unread-count
POST /notifications/{id}/read
POST /notifications/read-all
```

新增通知中心分页接口：

```text
GET /notifications/page
    ?type=TASK_DUE_SOON|TASK_OVERDUE
    &unreadOnly=true|false
    &currPage=1
    &pageSize=20
```

参数均可选；`type` 为空表示全部类型，`unreadOnly` 默认为 `false`，页码从 1 开始，`pageSize` 默认 20、最大 50。返回现有 `PageResult<UserNotificationDTO>`，记录按 `createdAt DESC, id DESC` 排序。接口仍使用统一的 `ResponseResult` 包装。

`UserNotificationDTO` 继续返回 `id/type/title/content/projectId/taskId/nodeId/actorId/actorName/readAt/createdAt`。任务提醒的 `actorId` 和 `actorName` 为空，前端根据 `type` 显示“任务提醒”标签；跳转目标使用已有通知路由，进入 `/projects/{projectId}?task={taskId}`。

## 4. 前端设计

### 4.1 通知中心页面

新增受 `project:read` 路由守卫保护的 `/notifications` 页面。页面包含：

- 全部、未读、临期、逾期四个筛选入口。
- 通知列表、分页、加载中、空状态和错误状态。
- “全部标为已读”操作，成功后刷新当前列表和顶部未读数。
- 未读通知有清晰的视觉标识；临期和逾期使用不同的状态标签，逾期优先使用风险色。
- 点击通知沿用现有深链逻辑打开任务所在项目；项目或任务不可访问时显示统一错误提示，不暴露底层 ID 细节。
- 文字内容按纯文本显示，不使用 `v-html` 或其他 HTML 注入路径。

页面在 390px 宽度下保持可读：筛选入口可横向滚动或折行，通知标题/正文允许换行，分页控件不溢出。

四个筛选入口互斥：全部表示所有通知，未读表示所有类型中的未读通知，临期和逾期分别表示对应类型的全部通知；第一期不提供“未读 + 逾期”这样的组合筛选。切换筛选时重置到第 1 页，翻页时保留当前筛选条件。`type` 传入未定义值时接口返回 400，不能静默当作全部。

### 4.2 顶部铃铛

保留现有 20 条预览和未读轮询，新增：

- 临期、逾期通知的类型标签和对应图标/颜色。
- “查看全部”入口，跳转 `/notifications`。
- 预览列表与通知中心共用类型标签、日期格式和深链规则。

通知中心不改变工作台的个人待办语义；工作台仍只展示当前用户的待办和参与内容，不因为通知扫描而展示全公司任务。

## 5. 测试与验收

### 5.1 后端自动化测试

必须覆盖：

1. 临期状态窗口是 `dueDate ∈ [today, today + N]`，默认包含今天至未来第 7 天共 8 个日期；未来第 8 天不属于窗口。临期通知只在进入窗口外沿当天（`dueDate = today + N`）的 09:00 触发，到期当天不发临期。
2. 新建/改期后只有 `dueDate = today + N` 才生成临期提醒，窗口内新建或改期的任务当天不发；任务昨天刚逾期（`dueDate = today - 1`）时生成逾期提醒，更早的历史逾期不补发；`DONE` 任务不生成。
3. 无负责人任务不生成；只给负责人写入收件箱。
4. 已删除任务、已完成/已终止/已删除项目下任务不生成。
5. 首次上线扫描不回填历史逾期；同一日期重复执行临期或逾期扫描不产生重复记录。
6. 截止日期变化只保证新的临期去重键可计算；只有改期当天落在 `dueDate = today + N` 才插入临期记录。进入逾期后按当地日期生成逾期记录，同一任务同一天最多一条。
7. 配置的时区、09:00 cron、默认 7 天窗口和非法配置行为可验证。
8. `/notifications/page` 的类型、未读、分页、排序和 `project:read` 权限生效；用户不能读取或标记他人通知。
9. V15 迁移在已有通知数据上成功，历史通知和现有通知接口行为保持兼容。
10. 通知列表的项目可读性、项目删除过滤、未读数和分页总数均由 SQL 条件保证，不存在“先切页再过滤”的缺页或错误总数。
11. 截止日期已在临期窗口内的新建任务当天不发临期通知；到期当天不发临期通知；窗口外沿当天和刚逾期当天各至多一条。

### 5.2 前端自动化测试

必须覆盖：

1. 四种筛选条件正确转换为 API 参数，翻页会重置/保留筛选条件符合页面约定。
2. 临期、逾期标签和未读状态正确显示。
3. 点击任务提醒使用现有项目/任务深链。
4. 加载中、空列表、接口错误和批量已读后的刷新状态可见。
5. 通知正文按文本渲染，输入中的 HTML 标签不会被解释执行。
6. 通知中心路由和铃铛“查看全部”入口可用，390px 视口不出现横向布局溢出。

### 5.3 人工验收矩阵

| 场景 | 预期结果 |
| --- | --- |
| 普通员工是未完成任务负责人 | 在任务进入临期窗口外沿当天或刚逾期当天的 09:00，各至多收到一条对应站内通知，并可打开任务 |
| 普通员工不是任务负责人 | 不收到该任务的提醒 |
| 任务完成后再次扫描 | 不新增提醒 |
| 同一任务同一天重复执行作业 | 未读数和通知条数不增加 |
| 更换负责人后执行作业 | 旧人不收新提醒，新人在符合触发条件的后续扫描收到；旧记录不收回、不改已读状态 |
| 项目终止后打开通知 | 不产生新提醒；历史通知仍可读取并打开项目内容 |
| 项目删除后打开通知 | 通知不出现在列表和未读数，深链按不存在处理，不返回暴露项目存在的 403 |
| 无 `project:read` 的账号 | 不能打开通知中心、列表、详情或通知深链 |
| 顶部铃铛 | 仍能看到预览、未读数和“查看全部” |
| 上线第一天 | 只产生当天新进入临期窗口和当天刚逾期的提醒；不回填历史逾期。铃铛仍只显示最近 20 条，提醒可能挤掉较早事件，但完整历史在通知中心可分页查询 |

## 6. 发布、迁移与回滚

实施顺序固定为：

1. 先补 V15 迁移和数据访问层。
2. 增加提醒服务、配置和调度作业，默认使用站内通知。
3. 增加分页接口并补权限/幂等测试。
4. 增加通知中心页面和铃铛入口。
5. 更新业务规范、使用手册、运维通知配置和发布检查清单。
6. 执行后端全量测试、前端测试/类型检查/构建、OpenAPI 与迁移一致性检查，再重启服务进行真实接口验收。

提醒作业发布时保持 `pms.notification.task-reminder.enabled=false`；只有项目权限收口完成、SQL 可读性过滤验收通过后，才在发布配置中显式改为 `true`。通知中心页面和历史通知查询可以先上线，但在开关关闭期间不会生成新提醒。

宿主机时区不是 `Asia/Shanghai` 时，提醒作业仍以配置的 `zone` 计算日期和 09:00 执行；现有工作台 `dueSoon` 仍按 JVM 默认时区计算，本期不改工作台数据范围和计算实现，因此午夜前后可能与通知中心相差一天，属于已知差异，后续统一时区时单独处理。

V15 只新增可空字段和索引，旧版本代码可以忽略新字段；回滚应用版本前应先停止提醒调度并确认没有新提醒写入，再按数据库备份策略处理索引/字段回退。不得通过删除 `user_notification` 记录来回滚功能，也不得清理用户已有的已读/未读历史。

## 7. 不在本期范围内

- 邮件、飞书、企业微信、短信、浏览器 Push。
- 用户自定义提醒时间、按项目关闭提醒、周末/节假日历法。
- 每日摘要、提醒升级、重复催办和通知模板管理。
- 把通知中心扩展成通用企业消息总线。
- 改变现有项目权限矩阵、工作台数据范围或反馈工单可见性。
