# 需求管理与单一执行对象关联设计方案

## 1. 方案结论

本次新增“需求管理”作为独立的研发管理对象。需求不是项目的下级对象，也不是专题或故事的别名，而是一个独立的业务入口和分析对象。

需求拥有自己的：

- 需求列表和详情页；
- 流程模板和已发布版本快照；
- 流程节点、节点负责人、节点排期、节点字段；
- 节点任务和子任务；
- 负责人、状态、进度和审计记录。

需求分析完成后，可以把需求落到一个执行对象上，但一个需求在同一时间只能有一个执行对象：

- 不关联任何执行对象；
- 关联一个项目；
- 关联一个专题；
- 关联一个故事。

不能同时关联项目、专题和故事，也不能同时关联其中任意两个对象。

本方案保留已经确定的项目、专题、故事层级关系，并把需求关系定义为“追踪关系”，而不是改变执行对象之间的父子关系。

## 2. 整体业务关系

~~~text
需求
└── 需求流程
    ├── 需求分析节点
    ├── 需求决策节点
    │   └── 执行对象组件
    │       ├── 未关联
    │       ├── 关联一个项目
    │       ├── 关联一个专题
    │       └── 关联一个故事
    └── 需求后续节点

项目
└── 项目流程节点
    └── 项目流程模板配置的运行时组件
        └── 专题
            └── 专题流程节点
                └── 故事拆分组件
                    └── 故事
                        └── 故事流程节点
                            └── 任务和子任务
~~~

其中：

1. 需求到项目、专题或故事的关系只表示“该需求最终选择了哪个执行落点”。
2. 需求关联项目后，项目下的专题和故事仍然按既有项目、专题、故事关系管理，不能因为需求关联项目就自动把需求复制到所有下级对象。
3. 需求直接关联专题时，不改变专题是否关联项目，也不自动建立项目关系。
4. 需求直接关联故事时，不改变故事是否关联专题，也不自动改变故事的专题节点归属。
5. 项目、专题、故事继续使用各自独立的流程实例和任务板。

## 3. 业务对象和生命周期

### 3.1 需求对象

需求的基础信息包括：

- 需求名称；
- 需求描述；
- 需求负责人；
- 优先级；
- 当前流程状态和流程进度；
- 当前唯一执行对象；
- 创建人、更新时间、版本号和删除状态。

需求创建时可以没有执行对象。此时需求处于分析阶段，仍然可以配置需求节点、填写节点字段和创建节点任务。

### 3.2 需求状态与执行决策分离

需求的流程状态由需求自己的流程节点决定，执行决策由是否存在唯一执行对象决定。二者不混成一个字段。需求表中的 status 只表示生命周期，初始值为 ACTIVE；本轮不增加独立的取消操作，删除仍由 deleted 软删除字段表达：

| 状态维度 | 取值 | 说明 |
| --- | --- | --- |
| 生命周期 | ACTIVE | 需求仍可维护；删除由 deleted 表达 |
| 流程状态 | 未配置、未开始、进行中、已完成 | 由需求流程模板和节点状态计算 |
| 执行决策 | 未关联、已关联 | 由当前执行对象是否为空决定 |

这样可以表达“需求正在调研但还没有决定做项目、专题还是故事”，也可以表达“需求已经选定专题，但需求流程还有后续验收节点”。

需求列表和详情页同时展示这两个维度，不使用“没有关联对象就代表需求异常”的含义。

### 3.3 目标对象有效性

执行对象类型和目标 ID 由服务端严格校验：

- 项目：只能关联状态为进行中的项目；已完成、已终止、已删除的项目不能作为新的需求执行目标。
- 专题：只能关联未删除的专题；专题是否绑定项目不影响它作为需求目标。
- 故事：只能关联未删除的故事；故事是否绑定专题不影响它作为需求目标。
- 目标对象必须在当前用户可见的数据范围内。
- 基础信息编辑接口不能绕过执行对象服务直接写目标类型和目标 ID。

项目状态判断复用现有 ProjectStatus.isOpen 规则，兼容历史项目状态 0 视为进行中，不在需求模块中复制一套状态判断。

## 4. 执行对象关联规则

### 4.1 唯一当前关系

需求表保存当前执行对象：

~~~text
execution_target_type: PROJECT | TOPIC | STORY | NULL
execution_target_id:   目标对象 ID | NULL
~~~

数据库层保证两个字段同时为空或同时有值；服务层保证目标类型和值匹配。

关联操作有三种：

1. 关联：当前未关联时设置一个目标。
2. 解绑：清空当前目标，需求仍保留。
3. 改绑：当前已有目标时，通过明确的“变更执行路径”操作换成另一个目标。

同一个需求不能通过并发请求产生两个当前目标。关联、解绑、改绑必须锁定需求记录，并在同一事务中完成目标校验、当前关系更新、历史记录写入和审计记录。

本轮执行对象组件默认关联已经存在的项目、专题或故事，不在组件内嵌套创建三类执行对象。这样可以先把“需求分析”和“执行路径唯一性”做稳定；后续如果需要“从需求一键创建并关联”，应分别复用项目、专题、故事的创建流程，再调用同一个关联服务，不能在前端直接拼装目标数据。

### 4.2 改绑策略

本方案默认采用以下策略：

- 需求仍处于未完成分析阶段时，可以直接关联、解绑或改绑。
- 需求已经选定执行对象并进入执行阶段后，不能通过普通编辑静默替换目标。
- 此时必须点击“变更执行路径”，填写变更原因，系统在事务中写入旧目标结束记录、新目标关联记录，并保留完整历史。
- 目标对象被删除或变为不可用时，需求不被级联删除，当前关系显示为“目标不可用”，需要用户通过变更执行路径修复。

改绑不会删除旧项目、专题、故事，也不会复制或删除目标对象的流程、字段、任务和成员。

### 4.3 需求与下游对象的展示

- 需求详情显示当前执行对象卡片和执行对象变更历史。
- 项目、专题、故事详情在统一的关系摘要区域显示直接来源需求。
- 目标列表可以增加“来源需求”列或筛选条件。
- 需求关联项目时，不在项目下所有专题和故事行上重复显示该需求。
- 需求关联专题时，只在该专题显示来源需求，不自动显示到专题下的故事。
- 需求关联故事时，只在该故事显示来源需求。

## 5. 需求流程模板

### 5.1 流程类型

在现有流程类型基础上增加：

~~~text
requirement-management / 需求管理
~~~

现有类型保持不变：

- general / 项目管理；
- topic-management / 专题管理；
- story-management / 故事管理；
- requirement-management / 需求管理。

流程模板页面进入时先选择流程类型，再选择模板。需求模板不配置项目挂载节点或专题挂载节点，因为需求本身是独立对象。

### 5.2 版本规则

需求创建时优先绑定一个已发布的需求流程模板版本快照：

~~~text
显式选择的已发布版本 / 默认模板版本
    ↓
创建需求
    ↓
保存 templateVersionId
    ↓
需求详情只读取该版本
~~~

规则与项目、专题、故事一致：

- 草稿不影响已有需求；
- 修改默认版本只影响新建需求；
- 创建时显式选择已发布版本时使用显式版本；未显式选择时使用当前默认版本；
- 没有默认版本且没有显式选择时，仍允许创建需求，但需求流程显示“未配置”，不能执行节点推进，待管理员配置后再继续；
- 发布新版本不会重写历史需求；
- 归档版本前必须检查是否仍被默认配置或需求实例引用；
- 模板中配置的节点、字段、运行时组件必须冻结到需求流程实例。

### 5.3 执行对象组件

增加一个运行时组件：

~~~text
requirement-execution / 需求执行对象
~~~

模板管理员可以把它放在需求流程的任意一个节点上。组件的职责是：

- 展示当前是否已关联执行对象；
- 按项目、专题、故事三种类型搜索可选对象；
- 关联已有对象；
- 解绑当前对象；
- 在满足条件时发起变更执行路径；
- 展示目标对象状态、负责人、进度和跳转入口；
- 展示关系变更历史。

组件位置由模板配置决定，代码不写死“需求分析”或“需求决策”节点名称。模板没有配置该组件时，需求仍可正常使用自己的节点和任务，但不能从详情页执行关联操作；详情页应给出统一的“模板未配置执行对象组件”提示。

组件只能使用已注册的 key 和受控属性，模板不能注入任意 HTML、CSS 或脚本。

## 6. 数据模型

### 6.1 新增需求表

新增 pms_requirement：

| 字段 | 说明 |
| --- | --- |
| id | 自增主键 |
| title | 需求名称 |
| description | 需求描述 |
| priority | 优先级 |
| owner_id | 需求负责人，可为空 |
| execution_target_type | PROJECT、TOPIC、STORY，可为空 |
| execution_target_id | 对应目标 ID，可为空 |
| status | 生命周期状态，初始为 ACTIVE |
| deleted | 软删除 |
| version | 乐观锁版本 |
| created_by / created_at / updated_at | 审计字段 |

数据库约束：

- execution_target_type 和 execution_target_id 必须成对为空或成对有值；
- execution_target_type 只允许 PROJECT、TOPIC、STORY；
- execution_target_id 不增加多态外键，目标存在性由目标服务校验；
- execution_target_type、execution_target_id 建联合索引，支持目标反查。

### 6.2 新增关联历史表

新增 pms_requirement_execution_target_history：

| 字段 | 说明 |
| --- | --- |
| id | 自增主键 |
| requirement_id | 需求 ID，外键指向需求 |
| action | LINK、UNLINK、REPLACE |
| target_type | 新目标类型；LINK/REPLACE 时为 PROJECT、TOPIC、STORY，UNLINK 时为空 |
| target_id | 新目标 ID；LINK/REPLACE 时有值，UNLINK 时为空 |
| previous_target_type / previous_target_id | 变更前的目标；LINK 时为空，UNLINK/REPLACE 时保存旧目标 |
| reason | 变更原因 |
| operator_id | 操作人 |
| created_at | 操作时间 |

历史表只追加，不更新旧记录。当前关系以需求表为准，历史表用于审计和恢复判断。

### 6.3 复用现有工作流表

现有 pms_development_item_workflow 的 item_type 扩展支持 REQUIREMENT。V54 已经把 project_id 和 source_node_id 调整为可空，以支持独立专题和故事；V56 只需要保留这项兼容性并让 REQUIREMENT 走无项目上下文分支，不重复执行破坏性的列变更。项目、专题、故事的上下文完整性继续由服务层校验。

需求工作流仍复用：

- pms_development_item_workflow；
- pms_development_item_workflow_node；
- pms_development_item_task；
- 节点字段 JSON；
- 现有乐观锁和任务父子结构。

这样可以确保需求、项目、专题、故事使用同一套详情渲染协议和任务归属规则。

## 7. 后端接口契约

### 7.1 需求基础接口

建议在 /development/requirements 下提供：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| POST | /page | 需求列表分页 |
| POST | / | 创建需求 |
| GET | /{id} | 获取需求流程详情 |
| PUT | /{id} | 编辑需求基本信息 |
| DELETE | /{id} | 软删除需求 |
| POST | /{id}/restore | 恢复需求 |

创建时可选传入已发布的 requirement templateVersionId；未传时使用默认版本，若默认版本也不存在则创建“未配置流程”的需求。编辑基础信息不接受 templateVersionId、executionTargetType、executionTargetId，避免绕过版本绑定、唯一关系和权限校验。

### 7.2 通用流程接口

扩展现有通用接口，使 type 支持 requirement：

- GET /development/requirements/{id}
- PUT /development/items/requirement/{id}/nodes/{nodeId}
- POST /development/items/requirement/{id}/nodes/{nodeId}/complete
- POST /development/items/requirement/{id}/nodes/{nodeId}/tasks
- PUT /development/items/requirement/{id}/tasks/{taskId}
- DELETE /development/items/requirement/{id}/tasks/{taskId}

需求、专题、故事共用同一个流程更新服务，差异只在 ItemContext 和权限/目标组件。

### 7.3 执行对象接口

建议提供：

- POST /development/requirements/{id}/execution-target/options：按目标类型和关键词分页查询可选项目、专题、故事；
- PUT /development/requirements/{id}/execution-target：第一次关联目标；
- DELETE /development/requirements/{id}/execution-target：解绑；
- POST /development/requirements/{id}/execution-target/change：带原因改绑；
- GET /development/requirements/{id}/execution-target/history：读取历史。

统一请求结构：

~~~json
{
  "targetType": "PROJECT | TOPIC | STORY",
  "targetId": 123,
  "requirementVersion": 0,
  "reason": "执行路径调整"
}
~~~

服务端对每种 targetType 使用对应的目标服务和权限服务校验，不接受客户端传入项目节点 ID、专题节点 ID 或故事专题节点 ID。

### 7.4 目标对象反查摘要

项目、专题、故事详情和列表的来源需求摘要由服务端根据需求表的当前目标反查生成，不在三个目标表中重复保存 requirement_id：

- 项目详情返回直接关联该项目的来源需求摘要；
- 专题详情和专题列表返回直接关联该专题的来源需求摘要；
- 故事详情和故事列表返回直接关联该故事的来源需求摘要；
- 没有直接关联时返回空，不沿项目、专题、故事层级递归传播。

实现上将“来源关系只读查询”和“目标关联写入”拆成两个服务边界。项目详情等基础服务只依赖只读查询服务；只读查询服务不依赖项目业务服务，避免项目服务和关联写入服务互相注入形成循环依赖。

## 8. 权限、审计和历史账号

### 8.1 权限

新增独立权限：

- requirement:read；
- requirement:write；
- requirement:manage。

现有项目、专题、故事的项目数据范围规则不被放宽。需求列表本轮按 requirement:read 权限读取公司范围内需求；查看目标摘要和跳转时，再按目标对象自身权限脱敏或拒绝跳转。后续若需要需求组织隔离，再单独增加需求组织字段和数据范围规则。

为了兼容现有管理员和项目管理员，权限种子迁移需要把需求权限加入对应内置角色；自定义角色不自动扩大权限，管理员可以在角色管理中显式授权。

### 8.2 审计

至少记录：

- 需求创建、编辑、删除、恢复；
- 需求模板版本绑定；
- 执行对象关联、解绑、改绑；
- 改绑原因、旧目标、新目标；
- 需求节点负责人、排期、字段和任务变更。

### 8.3 历史账号

历史需求、节点、任务和关联历史中的用户 ID 保留，不因用户停用或删除而丢失。展示时复用现有历史账号显示策略：

- 历史记录可以显示原名称或“已停用用户”；
- 新的负责人、节点负责人和任务执行人只能选择有效用户；
- 关联目标的变更不删除历史用户引用。

## 9. 统一 UI 规则

需求详情直接复用项目、专题、故事详情的基础壳层：

- 同一个页面背景色；
- 同一个详情头部、摘要区、流程条；
- 同一个节点详情卡片；
- 同一个负责人和排期编辑行为；
- 同一个节点字段渲染器；
- 同一个任务看板；
- 同一个空状态、错误状态和保存提示；
- 同一个运行时组件 host。

模板只能决定：

- 有多少个节点；
- 节点名称、描述和交付物；
- 节点字段；
- 已注册的运行时组件；
- 节点排序。

模板不能决定页面的整体背景、卡片层级、尺寸、间距、状态色和保存交互。新增需求详情必须通过现有共享组件渲染，不能复制一套独立页面 CSS。

需求列表沿用项目、专题、故事列表的 PMS 表格规范：

- 页面标题区和操作区；
- 搜索、状态、执行对象类型筛选；
- 统一表头、行高、分页、空状态；
- 操作列固定为详情、编辑、删除；
- 未关联需求显示“未关联”，不显示假项目或空路径；
- 执行对象列按类型显示项目、专题或故事名称，并支持跳转。

## 10. 异常和并发规则

- 需求被软删除后，不能新增、变更执行对象或编辑节点；恢复后可继续。
- 目标对象在搜索后被删除或状态变化，提交时重新校验并返回明确错误。
- 两个用户同时给同一需求关联目标时，只有一个事务成功；另一个返回冲突并要求刷新。
- 改绑过程中任何校验、历史写入、当前关系更新或审计写入失败，全部回滚。
- 模板默认版本未配置时允许创建需求但显示未配置状态；完成需求节点前必须由管理员配置有效模板。
- 模板发布后若执行对象组件配置在不存在的节点上，发布失败。
- 未知运行时组件不执行任意渲染，详情页显示降级提示并记录审计/迁移问题。

## 11. 本轮范围与后续范围

本轮实现：

1. 独立需求列表和详情页；
2. 需求流程模板类型和版本快照；
3. 需求节点、字段、任务和子任务；
4. 需求执行对象组件；
5. 需求与项目、专题、故事的单一关联、解绑、带原因改绑；
6. 统一列表/详情 UI；
7. 权限、审计、历史账号和文档；
8. 现有项目、专题、故事回归。

暂不实现：

- 一个需求拆分为多个项目、专题或故事；
- 需求之间的父子、依赖、重复、冲突关系；
- 自动根据需求内容生成项目/专题/故事；
- 将需求关系自动复制到目标对象的所有下级对象；
- 需求与任务的额外多对多关系；需求任务仍然属于需求自己的流程节点。

后续如果需要“一个需求拆分出多个执行对象”，应新增“需求拆分”领域模型，不能直接放宽当前唯一目标字段，否则会破坏本方案的追踪闭环和历史语义。

## 12. 逻辑闭环检查结论

业务链路闭环如下：

~~~text
创建需求
  ↓
选择需求流程模板版本
  ↓
在需求节点完成分析、字段和任务
  ↓
未关联 / 关联一个项目 / 关联一个专题 / 关联一个故事
  ↓
执行对象独立推进自己的流程
  ↓
需求详情可追踪执行对象，执行对象详情可反查直接来源需求
  ↓
需求流程完成或继续维护；删除/恢复属于独立的生命周期操作
~~~

这条链路没有把需求错误地变成项目下级，也没有让专题和故事重新回到同级；同时满足“需求可以先分析、之后再决定执行落点”和“一个需求只能关联一个对象”两个核心要求。
