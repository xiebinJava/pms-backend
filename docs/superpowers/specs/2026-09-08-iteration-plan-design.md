# 迭代计划替代里程碑设计

## 背景

项目当前在计划节点维护执行计划、资源和风险，在研发节点又使用里程碑承接专题，两个概念边界重叠。研发中的故事实际需要的是可执行的时间计划，而不是一个独立的项目里程碑对象。

## 目标

1. 在“计划、资源与风险基线”节点中维护结构化的迭代计划。
2. 研发故事可以选择所属迭代计划，也可以暂不关联。
3. 任务继续保持独立，不与故事或迭代计划强制关联。
4. 日常研发页面不再展示或要求填写里程碑。
5. 旧里程碑表和历史数据先保留，避免一次性破坏历史数据；后续如确认无历史兼容需求，再单独清理。

## 迭代计划字段

每条迭代计划属于计划节点，包含：

- 计划名称
- 负责人
- 目标/交付说明
- 计划状态（未开始、进行中、已完成）
- 开始日期与结束日期
- 排序

计划基线确认时至少需要一条完整迭代计划，并要求名称、负责人和排期完整。故事关联校验只允许选择当前项目、已确认计划基线中的迭代计划。

## 兼容策略

- 新增 `project_node_iteration_plan` 表，并在故事表增加 `iteration_plan_id`。
- 不删除 `project_milestone` 表和旧的专题里程碑字段；后端保留历史兼容字段，但新的研发接口不再读写它们。
- 前端移除研发专题的里程碑选择、项目协作里的里程碑入口和里程碑展示；旧数据不再出现在正常编辑流程中。
- 删除迭代计划时，如果已有故事引用该计划，后端拒绝删除并提示先调整故事关联，避免产生孤儿关联。

## API 形态

- `GET/PUT/POST /projects/{projectId}/nodes/{nodeId}/plan-resource-risk` 的响应和保存请求增加 `iterationPlans`。
- `GET /projects/{projectId}/iteration-plans` 返回已确认计划基线中的迭代计划，供研发故事选择。
- `NodeDevelopmentStory` 增加 `iterationPlanId` 与 `iterationPlanName`。
- `NodeDevelopmentTopic` 不再返回或接收 `milestoneId` / `milestoneTitle`。

## 生命周期

- 计划节点可编辑时，迭代计划与资源、风险一起自动保存。
- 计划节点确认后工作台锁定；节点回滚后恢复编辑。
- 研发节点只读读取已确认的迭代计划；未确认或方案决策发生变化时，故事选择器为空。
- 研发节点完成不要求每个故事都关联迭代计划，保留“先记录故事、后补排期”的灵活性。
