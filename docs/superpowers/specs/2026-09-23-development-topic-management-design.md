# 专题管理列表、维护与项目节点归属设计

## 背景与目标

专题管理列表目前呈现了过多的实现信息，且缺少与项目管理一致的编辑、删除入口。专题与项目、所属故事及各自的流程任务有关联，不能只改列表外观或只修改专题记录中的项目 ID。本次同时明确：专题流程模板可以配置专题归属项目流程的哪个节点；新建和改绑专题按该设置定位，已存在专题不因模板变化自动迁移。

## 已确认的产品规则

- 专题列表保留项目管理式的操作：详情、编辑、删除。专题名称也可进入详情。
- 编辑专题主要修改专题基本信息和关联项目；不要求用户在专题编辑表单中选择项目节点。
- 专题可改绑到任意符合条件的项目，但项目必须处于“进行中”。已完成、已终止、已删除项目不可选；后端必须再次校验，不能只靠前端过滤。
- 专题实际归属的项目节点由“专题管理”流程模板设置。当前默认目标是“开发测试与项目控制”；以后可由管理员改成其他项目节点。
- 故事始终继承所属专题的项目和项目节点，不单独选节点。
- 更改模板中的项目节点不自动迁移现有专题；当前已存在的专题保持原项目节点。新建专题及之后改绑项目的专题按当时生效的专题流程配置定位。
- 专题、故事详情中的流程 UI、未完成节点编辑能力、点击外部自动保存负责人/排期/字段等行为，沿用已确认的研发事项流程详情规范；本设计不重新定义这些行为。

## 列表体验调整

专题和故事列表继续共用列表页面，但按类型保留各自业务列。两类列表统一去掉：标题前图标、标题下数据库 ID、项目代码/项目节点副标题、状态下的流程状态副标题、进度下的研发进度副标题。专题列表额外移除“构建/测试”列。保留专题数、主要状态、主进度、负责人、项目上下文等仍有业务价值的信息。

专题列表操作列为“详情、编辑、删除”；已删除专题的操作为“恢复”。列表增加正常/已删除范围切换，让软删除记录有明确的恢复入口。故事列表沿用当前详情行为，不在本次扩展故事 CRUD。编辑/删除仅针对专题。

## 项目节点配置方案

考虑了三种建模方式：

1. 在专题流程模板版本中保存项目节点的稳定 `nodeKey`，按该 key 在目标项目中解析实际 `project_node`。目标项目没有该节点时，不允许绑定。优点是支持项目节点名称调整、已发布模板版本演进且可以继续允许跨项目改绑；局限是自定义项目流程可能不包含该 key。
2. 在专题模板里同时绑定某个项目流程模板版本和其中一个节点。配置明确，但改绑会限制到使用该流程版本的项目，与“可绑定任何进行中项目”的预期冲突。
3. 只按节点名称匹配。界面容易理解，但重名、改名和本地化会导致误匹配，不适合作为数据关联键。

建议采用方案 1：专题管理流程模板版本保存 `sourceProjectNodeKey`；配置器从已发布的项目管理流程定义中选择节点，显示节点名称、保存稳定 key。服务端在新建或改绑时，以该 key 查找目标项目实际节点。目标项目状态不为“进行中”或不存在该 key 时拒绝操作；项目选项接口应过滤到当前用户可访问、状态进行中且具有目标节点的项目。这样“任意项目”指任意满足项目状态及节点兼容条件的项目。

旧版专题模板没有 `sourceProjectNodeKey` 时兼容使用 `development-control`（“开发测试与项目控制”）作为默认值。节点配置属于不可变模板版本；新模板发布后只影响后续新建/改绑，不更改专题已有的 `project_id/node_id`，也不更改专题和故事各自已固定的事项流程模板版本。

专题从某项目节点工作台新建时，只有当前节点 key 与生效专题模板的 `sourceProjectNodeKey` 一致才允许创建；否则 UI 不显示新增专题入口或给出简明说明，服务端仍必须校验。故事创建继续使用所属专题的项目/节点上下文。

## 编辑和改绑数据规则

- 同项目只修改标题/负责人等基本信息时，保留当前节点归属，即使管理员后来更换了模板默认节点。
- 改绑到另一个项目时，在事务内校验源项目和目标项目的可写权限、目标状态、配置节点存在性，然后一次性更新专题、其全部故事及相关事项流程的 `project_id/source_node_id`；任何一步失败则整体回滚。
- 保留专题/故事原有的字段、状态、日期、故事排序、事项流程节点状态和负责人、任务/子任务、任务执行人，以及每个事项已固定的流程模板版本。`node_id` 更新为目标项目的配置节点。
- 清空仅对原项目有效的关联：专题 `milestone_id`、故事 `iteration_plan_id`。不要求新项目有同名里程碑/迭代计划，也不错误地把旧项目计划挂到新项目。
- 专题改绑不调整项目自身流程、不搬动项目级任务、不改变旧项目流程状态。专题和故事仍是独立研发事项；此处只改变它们所属项目及来源项目节点。

## 删除与恢复专题规则（已确认）

删除前明确展示该专题下故事数量，并说明专题会从正常视图移除、其故事也会暂时隐藏，但专题/故事流程节点、任务和子任务记录会保留。确认后只设置专题的软删除标记，不物理删除专题、故事、事项流程或任务；故事列表、详情和项目节点工作台在父专题被软删除期间不展示其故事。

提供“已删除专题”视图及恢复操作。恢复专题后，其原有故事及其流程/任务随专题重新可见；所有历史节点状态、任务和字段值保持不变。软删除与恢复均记录审计事件。已删除专题不能编辑、改绑或进入普通详情；不能因所属项目之后变为已完成/已终止而丢失恢复能力。此前项目节点工作台通过整体保存移除专题的路径也必须改为软删除专题，不能再物理级联清除专题流程数据。单独从仍有效专题中移除故事的既有行为不在本次扩大为故事软删除。

## 权限与并发

- 列表展示和项目选项沿用当前数据范围；编辑/删除需要源项目的可管理权限，改绑还要求目标项目可管理。
- 服务端不信任前端传来的节点 ID、项目状态或 template version；项目节点由当前生效的专题配置和目标项目自身节点解析。
- 事务内重读/锁定专题、故事和流程关联并进行一致性校验；阻止客户端把不属于该专题的故事或流程一并移动。
- 删除和改绑写审计记录，包含专题 ID、原/新项目与节点、连带故事数量等必要信息，不记录无关流程字段内容。

## 接口与界面边界

- 专题列表数据增加/复用编辑所需基本字段；增加可搜索的进行中项目选项接口，按当前配置节点过滤。
- 增加专题更新和删除接口。更新请求只提交专题基本信息和目标项目 ID，不提交目标节点 ID；后端计算节点。
- 为专题表增加默认未删除的软删除标记；所有普通专题/故事查询排除已删除专题及其故事。增加已删除专题查询和恢复接口，恢复只清除专题的软删除标记，且不要求源项目仍处于进行中状态；访问恢复操作仍需满足专题治理权限。
- 流程模板接口在专题类型定义中读写 `sourceProjectNodeKey`，并提供受限的项目流程节点候选项。
- 列表编辑弹窗包含专题基本信息、关联项目；删除弹窗显示级联影响。成功后刷新当前页，并在当前页变空时回退一页。
- 项目节点工作台根据专题绑定配置控制专题创建入口；历史专题展示仍以其记录中的实际节点归属为准。

## 验收标准

1. 专题/故事列表副标题和专题“构建/测试”列按本设计移除；正常专题操作列可进入详情、编辑和删除，已删除专题可恢复。
2. 编辑专题基本字段但不改项目时不改变项目节点归属；改绑表单不要求选择节点。
3. 已完成/已终止/已删除项目无法在选项中选择；即使请求绕过 UI，服务端仍拒绝绑定。
4. 目标项目缺少模板指定节点时改绑失败且数据不变；有效改绑后，专题、全部故事及事项流程统一指向目标项目节点，专题/故事原独立流程和任务保留。
5. 改绑后清空旧里程碑/迭代计划引用；其他专题/故事内容及任务不变。
6. 发布专题模板新版本后，现有专题的位置和流程版本不变；后续新建或改绑按生效配置处理。
7. 删除影响数量在确认前可见；确认后专题及所属故事从正常视图隐藏，但原记录、事项流程和任务均保留；恢复后可重新查看且数据不变。
8. 专题只能在配置的项目流程节点下新建；故事使用所属专题上下文。
9. 越权访问、并发编辑冲突、事务失败均不造成部分迁移或部分删除。

## 实施阶段建议

1. 后端节点配置模型与候选项校验：模板定义兼容、候选节点读取、旧版默认 key，以及项目节点解析服务；完成后自审模板兼容和状态规则。
2. 后端专题更新/删除领域操作：事务性迁移专题/故事/事项流程，清理项目局部引用，权限、状态、审计与并发测试；完成后自审数据一致性。
3. 前端模板配置与专题创建入口：选择项目节点、根据配置控制创建入口；完成后自审自定义/历史模板展示。
4. 前端列表与专题维护：统一列表清理、专题编辑/删除、活跃项目选择和影响确认；完成后自审与项目管理的操作体验一致性。
5. 前后端定向测试、构建及关键页面验证；汇总未通过项和边界。

## 已确认决策

- 所选项目节点在目标项目不存在时，该项目不出现在可改绑选项中，服务端也拒绝改绑。
- 删除专题使用可恢复的聚合软删除，隐藏其故事但保留专题/故事流程及任务；从已删除专题视图恢复时一并重新展示故事。
