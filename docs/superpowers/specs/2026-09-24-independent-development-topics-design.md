# 独立专题与可选项目关联设计

## 背景与目标

专题当前强制关联一个项目及其流程节点，专题负责人、流程节点负责人和任务执行人也受项目成员范围限制。产品规则现已明确：专题可以独立存在；项目关联可以为空，专题负责人不由项目成员关系决定；未关联项目的专题对所有具有研发查看权限的用户可见。独立专题仍应有专题流程、节点任务和所属故事，并可在之后绑定或解除项目关联。

本设计扩展现有专题、故事和研发事项流程模型以支持可空项目上下文，不创建平行的“独立专题”子系统，也不伪造隐藏项目或项目节点。

## 已确认规则

- 创建专题时，名称必填；负责人可选，候选人为公司内状态为 `ACTIVE` 且未删除的用户；项目关联可选。
- 负责人、节点负责人和任务执行人均从全公司可用人员中选择，不以是否为关联项目成员作为前置条件。分配人员不会自动授予其项目访问权限。
- 未关联项目的专题及其故事，对所有具有研发查看权限的用户可见，不按项目成员范围过滤。修改/删除仍需研发编辑权限；已关联项目的专题继续遵守该项目的读取和写入权限。
- 无项目专题仍可绑定已发布的专题默认流程，展示其流程节点，并管理节点负责人、排期、模板字段、任务与子任务。
- 故事始终属于一个专题。专题未关联项目时，故事的项目/项目节点上下文也为空；专题绑定项目后，故事继承专题的项目和配置节点。
- 绑定项目时项目必须处于进行中，并且包含专题流程模板配置的目标项目节点；目标节点仍由稳定 `nodeKey` 解析，前端不提交可伪造的节点 ID。
- 编辑时可把已有专题从项目改绑到另一个合格项目，也可解除项目关联。解绑不删除专题/故事/流程/任务数据。
- 每个专题/故事已实例化的流程继续固定其流程模板版本。模板版本变化不自动改变现有流程、项目关联或项目节点。

## 方案比较

1. **现有关联列允许为空，并使流程服务支持无项目上下文（采用）**：保留现有专题、故事和流程实例身份及外键，只将项目上下文改为可空；以事项及模板版本作为流程主关系。一次迁移覆盖数据库、服务端校验、查询和前端呈现，保持已关联数据原样。
2. **新增独立专题/故事/流程表**：隔离模型但复制现有列表、详情、任务、软删除和审计逻辑，后续两套模型容易分叉。
3. **表单允许不选项目，但先禁用流程和故事，直到绑定项目**：数据库影响较小，但专题创建后并非完整可用事项，不符合独立使用需求。

采用方案 1。项目及节点是可选的来源上下文，不是专题、故事或其流程实例的身份依据。

## 数据关系与生命周期

### 独立创建与运行

- 新专题写入 `project_node_development_topic` 时 `project_id`、`node_id` 均可为 `NULL`；仍初始化基本专题状态与创建审计信息。
- 专题流程实例在 `pms_development_item_workflow` 中仍由 `(item_type, item_id)` 唯一标识，并固定已发布默认模板版本；`project_id` 与 `source_node_id` 均可为空。
- 流程节点、节点字段值、任务和子任务仍关联流程实例及其节点，不依赖项目表。无项目专题仍可通过事项流程维护完整交付过程。
- 故事仍通过 `topic_id` 必须关联专题；故事自身的 `project_id`、`node_id` 可空，并在创建/更新时从所属专题派生。故事流程实例采用相同的可空项目上下文规则。
- 缺少专题默认已发布流程模板时，沿用专题创建的既有校验：拒绝创建并提示管理员先发布、设为默认；不创建无模板的半成品专题。

### 绑定、改绑与解绑

- 新建时未选项目：保存空项目上下文并初始化专题流程；不要求创建人之后补绑项目才能使用专题流程和任务。
- 新建时选项目：验证项目为进行中、操作者可管理项目、目标节点存在，再以该项目及节点初始化上下文。
- 由无项目改为有项目，或在两个项目间改绑：在单个事务中锁定专题、所属故事、专题/故事流程实例及流程任务；解析专题模板当前配置的稳定项目节点 key；更新专题、故事和对应流程实例的上下文；清空只对旧项目有效的 `milestone_id` / `iteration_plan_id`。任一校验或写入失败则整体回滚。
- 解绑：在单个事务中清空专题、故事及其流程实例的项目/节点上下文，并清空里程碑/迭代计划引用；保留故事、模板版本、流程节点状态、字段值、负责人、任务/子任务及审计历史。解绑不修改事项内部的流程节点 ID，因为那些是事项流程节点，不是项目节点。
- 对已经关联项目的记录，模板之后更改绑定节点不自动迁移现有记录；只有该专题被明确改绑时才按当时配置重新解析节点。

## 权限和人员选择

- 专题、故事和流程详情 API 仍要求已有研发模块权限。项目关联为空时，列表及详情以 `PROJECT_READ` 为访问边界，不要求成员加入任一项目；已关联事项仍使用既有项目读取权限。
- 无项目专题的维护、流程节点编辑、任务增删改和节点推进使用 `PROJECT_WRITE`。有项目事项还必须满足对应项目写权限。软删除/恢复遵循现有专题治理权限，并且未关联项目时不可调用项目 ACL。
- 负责人、专题/故事流程节点负责人及任务执行人接受全公司 `ACTIVE`、未删除账号，不调用 `requireProjectMember`。服务端必须独立验证用户存在且可用；不能只依赖前端下拉过滤。
- 若已指派人员之后停用，历史负责人和任务执行人继续展示为历史值；不因读取详情而清空。停用人员不能作为新指派或变更后的目标人员。
- 所有人员选择器复用现有 `/users/search` 全员搜索和远程搜索交互；搜索结果只呈现可用账户，已保存的停用历史指派以只读历史标签展示。

## 列表与详情体验

- 专题列表混合展示当前用户可读的项目专题以及全部未关联项目专题；删除列表同样包含用户可治理的无项目专题。
- 项目筛选只筛选已关联该项目的专题，不关联任何项目的专题不会被隐式放入某个项目结果。
- 无项目专题的项目列展示“未关联项目”，不渲染项目或项目节点链接；有项目专题继续显示项目和模板配置的项目节点。
- 故事列表随父专题读取权限展示；项目、节点为空时显示“未关联项目”，项目筛选不命中这些故事。
- 专题详情页无项目时省略来源项目/项目节点链接，但保留专题流程摘要和节点详情；故事详情页保留所属专题链接，项目上下文按可空值显示。
- 创建与编辑表单中的项目字段是可选项；负责人选择不依赖项目选择，修改项目关联也不清空负责人。

## 兼容性与迁移

- 新增 Flyway 迁移修改专题、故事和事项流程表的 `project_id` / `node_id`（流程表对应 `source_node_id`）为可空；保留原有外键、索引和所有已存非空值。历史迁移文件不回改。
- Java DTO/实体和前端类型表达项目 ID、节点 ID 可空；详情、列表、审计和项目工作台对 `NULL` 上下文显式处理，不做对空值的解引用。
- 项目工作台派生专题组件仅针对实际绑定到项目节点的专题显示；无项目专题不占用、也不虚构项目节点。
- 现有已绑定专题/故事、正常列表、项目筛选、改绑及项目节点工作台行为保持不变。新增无项目路径不能扩大已绑定项目事项的数据读取范围。
- 删除/恢复专题沿用现有软删除规则；父专题删除时隐藏其故事但保留流程与任务，恢复时重新显示。

## 不在本次范围

- 创建新用户、改变账号状态规则或授予项目成员/项目读取权限。
- 修改项目本身的流程、节点、项目任务及其看板。
- 新增专题/故事的全局统一看板、通知策略或跨专题任务汇总。
- 更换已创建专题/故事绑定的流程模板版本，或因模板发布自动迁移既有专题的项目上下文。

## 验收标准

1. 不选择项目也可创建专题；负责人候选来自公司所有 `ACTIVE` 且未删除账户，选择负责人不触发项目成员校验。
2. 无项目专题仍绑定已发布专题默认模板；专题详情可读取流程、编辑所有未完成节点、维护字段和节点任务，刷新后数据保留。
3. 具有研发查看权限但不属于任何项目的用户，可以在专题列表、删除列表及详情查看无项目专题；不能据此读取其无权查看的项目专题。
4. 修改专题负责人、流程节点负责人或任务执行人时服务端拒绝不存在、停用或删除的账户；此类分配不授予项目访问权限。
5. 绑定项目时，只允许进行中且含模板目标节点、且操作者有管理权限的项目；专题、所属故事及流程实例上下文一致更新，所有流程和任务历史保持不变。
6. 解绑项目后专题、故事、事项流程的项目/节点上下文为空，里程碑与迭代关联被清理，流程节点/字段/任务保留；页面显示“未关联项目”。
7. 现存非空项目关联在迁移后完全保留；已有项目专题的读取、写入权限及项目节点组件派生行为不回归。
8. 并发绑定/解绑、无效项目、缺少配置目标节点和部分写入失败均不会留下专题/故事/流程上下文不一致。
