# 四项基础建设实施与验收记录

按以下顺序实施。每项分别评审仓库规范和方案符合性，修正发现的问题后再进入下一项。

| 顺序 | 交付 | 验收依据 |
| --- | --- | --- |
| 1 | 补齐分页接口契约 | Spring 实际路由与 OpenAPI 清单对照，真实响应通过契约校验 |
| 2 | 专题、故事改用数据库分页 | 三种角色的新旧响应逐页对照，两档规模下测量 P95 |
| 3 | 每套实例独立的首次管理员凭据 | 新装、重试、升级、受限会话、改密和重新登录 |
| 4 | CLI 版本采用包元数据 | 在源码目录外安装实际发布包，执行版本、帮助和诊断命令 |

## 接口契约

覆盖专题、故事、需求的三个 POST 分页接口及需求的兼容 GET。契约回归包含筛选结果、空页、默认参数、未登录和权限不足。路由对照测试按 HTTP 方法与 Spring 路径逐项核对。仓库原有的 87 项未描述路由记录在 `src/test/resources/openapi-route-debt.txt`。补录旧路由时同步移除对应记录。

## 数据库分页

旧实现基线为 `47e47c2`。在 JDK 17、MySQL 8.4 上使用相同的确定性夹具。管理员、项目成员和无可读项目用户的完整序列化响应与基线一致，涵盖连续页、末尾空页、每页 1 或 100 条、非空来源需求及流程摘要。另有用例覆盖字面百分号与下划线、负责人历史空白、软删除项目和越界页。旧数据中的故事如无专题但仍有项目归属，现按该项目的读取权限展示。

每个规模用同一关键词取第 3 页的 10 条，预热 2 次，清除 MyBatis 一级缓存后采样 20 次。下表为本机完成历史故事权限修正后的测量值。此前一轮在同样的 2 万故事负载上测得 34.6 ms。两版在四组负载上的完整响应 SHA-256 一一相同。

| 新增可见项目 / 节点 | 专题 / 故事 | 专题旧 → 新 P95 | 故事旧 → 新 P95 |
| --- | --- | --- | --- |
| 20 / 20 | 1,000 / 10,000 | 47.7 → 7.8 ms | 93.3 → 18.9 ms |
| 40 / 40 | 2,000 / 20,000 | 60.4 → 12.4 ms | 226.8 → 31.1 ms |

`DevelopmentPageBenchmarkTest` 可重建两档夹具并输出四条实际 Mapper 查询的 `EXPLAIN ANALYZE`。关键词检索仍需扫描候选行，数据库完成排序和 LIMIT，只把当页 ID 送入流程、来源和故事摘要查询。执行命令为 `mvn -Dpms.pageBenchmark=true -Dtest=DevelopmentPageBenchmarkTest test`。[两档数据的八份查询计划](2026-11-27-pagination-explain.txt)


## 首次安装凭据

Flyway V74 给已有账号保留原密码与授权。用 V73 的真实数据库验证了升级后管理员哈希、原有角色绑定、再次初始化及正常登录。仅有软删除账号的历史数据库也跳过首次引导。受限管理员的浏览器刷新可续期，业务接口、CLI 授权和 CLI 续期会被拒绝。改密事务撤销全部现有会话。

默认发行安装将口令写入同目录的 `.pms-bootstrap-admin-password`。使用 `ENV_FILE=.env.staging` 时使用单独的 `.env.staging.pms-bootstrap-admin-password`。首次登录并完成改密、用新密码验证访问后应删除交接副本。保留初始化完成标记，清除旧的显式配置值。发行运维测试覆盖两个安装、同目录不同环境文件、中断重试、显式口令、0600 文件权限、脱敏输出和交接副本销毁后重启。

配套发布三个仓库的候选版本。回退至忽略改密标记的旧后端前，先隔离业务入口并处置仍待改密的管理员会话。当前 1.2.0 发布标签与镜像不含这些工作区变更。

两个带空 MySQL 8.4 卷的本地 Compose 项目各自完成了安装和中断后重试。候选 JAR 和前端静态产物使用项目的 Java 17 与非特权 Nginx 运行镜像，在回环地址上联调。Chrome 在两个实例上分别完成首登、改密前直接访问项目页被引导回改密页、改密后重新登录并访问项目列表。销毁两个交接副本并重启后，数据库中的新密码哈希保持原值。此次验收还修复了上传卷第二次初始化时递归调整属主的权限错误。

## CLI 发布包

根 `package.json` 是版本来源。生产构建和源码运行使用同一字段，测试保留业务子命令中实体版本参数的含义。Node 22 测试运行正式构建命令和 `npm pack --json`，核对包内元数据，在源码目录外用 npm 安装生成的压缩包，并以安装生成的 `pms` 命令执行 `--version`、`--help` 和 `doctor --format json`。在临时源码副本中只改版本后重复同样的步骤。

| 根包版本 | 已安装命令的标准输出 | 帮助与 JSON 诊断 |
| --- | --- | --- |
| 0.1.2 | 0.1.2 加换行 | 通过 |
| 0.0.0-smoke.1（临时副本） | 0.0.0-smoke.1 加换行 | 通过 |

CI 会把候选提交号、包名、版本、SHA-512 完整性校验值及三条命令的结果写入作业摘要。本地复验入口为 CLI 仓库中的 `pnpm typecheck` 和 `pnpm test`。

## 深度复核修复

- V74 回退在隔离 Compose 实例上验证。候选后端已迁至 V74，随后故意令候选前端健康检查失败。发行脚本将备份恢复到另一数据库和上传卷，由 V73 后端通过就绪检查。测试数据和附件内容保持一致，V74 原数据仍在。
- 运维脚本的回归测试覆盖密钥随机源首次失败、随后恢复的重试，以及恢复报错时保持应用停止。
- MySQL 分页在排序前校正 Java 与 MySQL 的 Unicode 大小写匹配差异。回归用例覆盖希腊语词尾、带点大写 I、Kelvin 符号、过滤总数和第二页。四组基准响应哈希仍与旧实现一致。40 项目、2 万故事的故事分页本轮 P95 为 57.4 ms，旧 Java 实现为 226.8 ms。
- 后端集成工作流先在新库运行首次改密浏览器用例，再用改好的密码运行 API 和其余浏览器检查。本机使用同样的账号和密码参数验证。工作流使用配套前端源码。


## 回退与排序规则回归

- 在环境文件中保留独立的手动恢复卷配置，复跑升级回退。自动回退使用单独生成的目标卷，核对后端实际挂载和目录可读性后才启动前端。故意挂载错误卷时，前端保持停止。
- 本地 Compose 实测 V74 迁移成功、首次恢复导入中断。重跑只从原始 V73 备份恢复。V73 数据、附件内容和就绪接口均通过验证，V74 数据保留。重跑退出状态仍表示请求的升级未完成，脚本日志明确标记已恢复的旧版。
- MySQL 集成测试对项目和标题列配置不同的 utf8mb4 排序规则。修复前复现 1267，修复后专题和故事的匹配总数与第二页均通过。后端全量测试 1,277 项通过、6 项跳过。
