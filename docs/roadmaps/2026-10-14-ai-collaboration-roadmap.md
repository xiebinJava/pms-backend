# PMS 人与 AI 协作产品路线图

日期：2026-10-14（Asia/Shanghai）

状态：建议路线图，供确定下一阶段范围；不是已批准的工程实施计划，也不表示下列能力已经交付。

## 1. 产品方向与成功标准

用户已明确：主要探索人与 AI 协作的下一代管理系统，希望通过自然语言聊天实现项目推进。

产品定位：用户表达目标，AI 在授权范围内读取背景、准备成果并执行操作，PMS 管理业务事实、权限、流程与交付证据；人能查看进展、修订成果和做关键决策。

首批使用对象暂按熟悉自身业务的研发/产品团队考虑。先利用外部 AI 工作台和现有 PMS 页面验证，不以建设多企业商业平台为当前目标。

产品效果用“从目标提出到正确交付”的完整过程衡量，包括解释背景、等待、纠错、核验和返工。聊天次数、命令数量、填表数量均不作为核心成效。

三项原则：

1. 信息效率：减少重复解释、找资料和同步状态。
2. 体验效率：自然语言适合表达复杂目标，点击适合选择、查看、精确修改；两种交互共享业务事实。
3. 流程效率：先删除重复记录和无效步骤，再自动化必要工作。

本路线图根据源码和文档静态检查制定，本次未执行模型自然语言实验、真实写入验收或性能测量。

## 3. 路线选择

优先沿用“外部 AI 工作台 + PMS CLI + 现有 PMS 图形界面”。它与当前实现相符，能最快验证业务价值。对外呈现一致的场景成果和实际回读结果，不要求用户了解命令、节点编号或协议。

PMS 内置聊天可以在外部工作台的登录、上下文传递和结果修订成为主要障碍时评估。统一 Agent 平台、模型供应商管理和多 Agent 调度等，等待真实场景证明需求后再立项。

分阶段推进，阶段时间取决于可投入人力；每一阶段以验收结果决定是否扩展，暂不作日历交付承诺。

## 4. 第一轮：让一个场景有用且可信

### M0：建立现状清单与评估基线

交付：一份能力状态表、一组代表性需求、一份人工完成基线。

- 将每项能力标记为“代码已有 / 契约测试已通过 / 真实环境已通过 / 模型自然语言已验证”，记录版本和证据。
- 选取 10—20 条具有代表性的需求，覆盖背景充分、信息不足、术语歧义、已有分析、多个候选节点和权限不足等情况。
- 记录人工方式的主动投入时间、总完成时间、澄清次数、遗漏与返工。
- 预先制定分析质量评分表：问题/场景明确、范围可判断、验收条件可检查、假设有标记、关键缺失信息有指出、来源可追溯。

退出标准：团队知道当前能可靠做什么，且已有可用于对照的基线。历史测试记录不直接替代当前版本核验。

### M1：补齐首批场景需要的真实上下文

交付：AI 能准确识别目标、实际状态、可写范围及保存方式。

- 项目 context 从实际项目节点读取 ID、状态、版本、负责人、已有工作台内容；区分模板定义与执行状态。
- 为需求分析明确对象版本、当前节点版本、模板版本，不能用模板版本代替写入版本。
- 暴露当前组件实际配置、可写字段、保存规则与相关对象；保留现有接口的兼容性，不由客户端伪造缺失内容。
- 区分“当前用户无权读取”“尚未配置”“没有值”“数据未加载”，避免让 AI 把未知当不存在。
- 优先返回简洁摘要与可继续读取的资源引用；全部信息读取执行同一数据范围校验。
- 对单一当前可写节点允许由可信上下文解析；存在歧义时只提出必要澄清，不默认选列表第一项。

退出标准：明确目标的查询返回精确对象；节点、字段与页面回读一致；未授权信息不会泄露；陈旧版本的新写入被拒绝；缺失数据如实表达。

### M2：做深“需求分析 → 可评审成果 → 保存回读”

交付：一个能反复使用的自然语言业务场景，复用已有 CLI 入口，不重建保存系统。

示例请求：

> 分析这条需求，结合已有关联背景，准备范围、验收条件、风险和待决策问题，保存到当前可写节点。

- 输出简洁的事实摘要、分析成果、推断/假设和待决策事项，关键结论带依据；不得虚构来源。
- 明确成果可进入评审的质量标准。未解决问题可以作为待决策事项保存，不以生成更多文字作为完成条件。
- 用户仅要求分析时输出草稿；明确要求分析并保存时沿用既有授权执行。授权范围内不新增逐次人工确认弹窗。
- 分析保存不自动包含批准、完成节点、修改业务归属或改变交付承诺。更大的委派需要明确结果、范围和停止条件。
- 保存语义明确区分补丁、追加和替换；保留既有正文及未授权字段，保护人的修订。
- 保存前处理版本变化；执行后回读实际内容与版本。区分“执行失败”“写入成功但回读失败”“结果未知”，避免重复写入。
- 先用现有业务页面检查和修订成果；新增结果卡片仅解决实际观察到的核验/修订困难。卡片或按钮与聊天使用同一业务规则。

退出标准：事实/推断边界清楚，成果按评分表达标，授权保存后页面可见；重复请求不重复产生业务效果；用户能直接修订结果。

### M3：验证效率收益，决定继续或调整

交付：一份对照报告和经过复现的失败案例清单。

- 用难度相当的需求对照人工方式与 AI 方式，交替使用顺序，降低学习效应；在同一评分表下评估成果。
- 记录人的主动投入、总完成时间、修订次数、成果质量和执行可靠性；记录模型、工作台、Skill/接口版本。
- 部分用例重复执行，观察模型结果波动。API/契约测试不能代替实际自然语言轮次。
- 实验目标：主动投入时间下降 50%，质量不下降。该数字是待验证目标，不是已实现收益或推广承诺。
- 技术边界用程序检查；分析质量由熟悉业务的人评审。模型评分只能作为辅助，不能单独决定业务验收。
- 在所测边界用例中，越权写入、重复业务写入和未授权字段覆盖必须为零；样本无错误不等于生产环境零风险。
- 若结果没有改善，按失败分布修复上下文、交互或分析流程，再测；收益未明确前不扩大场景范围。

退出标准：获得可复现的收益与边界证据。达到目标后再扩大试用；未达到时给出具体调整及新实验，而非继续堆功能。

## 5. 第二轮：从成果准备扩展到跨对象推进

### M4：会议纪要转行动项与项目计划变更

前提：需求分析已有稳定收益，多个业务对象的读取、写入和回读可靠。

交付：用户提供纪要和明确项目，AI 提取行动项、匹配已有任务、准备变更并在授权范围内执行。

- 首版直接接受用户提供的文本或既有可读文档；自动入会、录音、妙记抓取等作为独立集成需求。
- 区分明确决议、讨论建议和推测；负责人及关键日期不猜测。
- 展示新增、修改、重复项与冲突，允许用表格或卡片直接选择和修订。
- 先限制为一个项目和受控数量的操作；尽量复用已有批量命令及事务边界。
- 涉及上线承诺、责任调整或范围变更且授权不明确的条目列为待决策，其余在明确授权范围内执行。

退出标准：行动项遗漏和误关联不高于人工基线，重复纪要不会重复创建任务，保存结果与计划页面一致。

## 6. 第三轮：持续跟踪与可靠委派

### M5：项目阻塞检查与持续工作记录

前提：用户反复需要持续跟踪、跨次继续或事件触发，且已有场景质量稳定。

交付：系统可解释阻塞原因、影响及建议下一步；人能查看一次完整 AI 工作的状态。

- 先从明确的规则识别逾期、缺失交付物、未决问题和依赖变化，再由 AI 解释并准备行动。
- 增加最小工作记录：目标、业务对象、人类负责人、执行者、授权范围、输入版本、状态、阻塞、成果和验证结果；关联已有 operationId。
- 长时间工作支持取消和重新校验后继续；不让单次接口成功直接代表整项工作完成。
- 先以用户主动触发检查验证价值。需要无人值守时再补事件持久化、重试、去重和监控；现有 webhook 失败日志不能替代可靠投递。
- 在授权范围内只对有意义变化给出提示，避免重复催办；未验证的 AI 推断不直接变成项目事实。
- 第一条外部证据连接优先选择与团队已有工作最接近的来源，例如代码 PR、测试报告或验收文档，并记录来源和时间。

退出标准：阻塞判断有依据，提醒有行动价值，失败可追踪，恢复不重复执行，人能随时介入。

## 7. 近期聚焦与延后事项

近期投入集中在上下文、需求分析场景、真实自然语言验收和结果修订体验。

以下事项在出现明确需求或验证收益前延后：

- 全量 REST API 一对一转换成 CLI 命令。
- 自建模型供应商平台、通用 Agent 调度器和大量角色 Agent。
- 重做整个 PMS 前端或强制所有操作改为聊天。
- 为 AI 单独复制业务规则或建立第二套业务成果真源。
- 对所有企业采用同一套完整流程，或未经观察就自动推进全部节点。
- 多企业 SaaS、计费和大量远程接入协议等商业化扩展。

权限、版本、幂等、审计、明确授权范围和真实回读是可信执行的必要条件，不能为压缩步骤而删除。

完成证明：实际身份、输入/输出版本、指定业务对象、执行记录、页面回读、重复请求结果、原有内容保留、模型自然语言成果及人工质量评价均可检查；没有运行的部分明确列出。

## 10. 2026-10-15 实施状态

需求分析编排 MVP 已完成真实隔离验收：结构化 `AnalysisDraft` 契约、AI 上下文读取边界、请求内授权去重、草稿引用与受保护字段校验，以及 preview/execute/readback 场景编排均接入真实 PMS。一次性数据库中的保存、幂等重放、版本冲突和结果回读通过；共享开发数据没有作为测试夹具。

真实证据和边界说明记录在 `docs/agent-contracts/pms/requirement-analysis-acceptance-report.md`。其中一个重要接口事实是：旧版本新幂等键当前返回 HTTP 409，Connector 必须把它呈现为未写入并要求刷新预览，不能自动盲重试。

本轮已经补齐 `AnalysisDraftProvider` 抽象、固定 Mock 和 OpenAI-compatible 外部模型实现，但没有配置外部模型凭据，也没有完成人工时间和质量基线。`pms-ai-connector/tests/fixtures/requirement-analysis-shadow-cases.json` 提供了 12 条自然语言影子用例和评分检查项，但不能代替真实模型运行。因此下一步先完成影子实验和人工对照，再决定是否做复用同一场景 API 的“草稿 → 预览 → 确认”最小入口；暂不开发完整聊天工作台、自动推进或无人值守执行。

### 2026-10-15：AI Orchestrator v1 垂直切片

本轮已补齐“会话 → 上下文快照 → Agent Draft 校验 → 计划 → 预览 → 确认 → 执行 → 回读验证 → 有序事件”的确定性编排层，首期只支持 `REQUIREMENT_ANALYSIS_SAVE`。后端复用既有 PMS 命令和 `pms_ai_operation`，Connector 提供六个客户端方法，CLI 提供 `scenario requirement-analysis orchestrate` 的机器可读薄入口；没有把模型配置放进 PMS Backend 或生产 CLI。

服务、持久化、控制器、Connector 客户端、CLI 契约和类型/构建检查已通过。真实隔离写入验收入口已补齐，但本轮未启动一次性数据库/API，也未配置隔离写入门禁，因此真实 preview/confirm/幂等/冲突/回读结果记为 SKIPPED，详见 `docs/agent-contracts/orchestrator/ai-orchestrator-v1-acceptance-report.md`。在该验收通过和自然语言影子质量基线完成前，继续延后完整聊天工作台、SSE 和自动推进。
