# PMS 业务规范与后端设计逻辑

## 1. 文档定位

本文档是 PMS 后端的业务规则和数据边界说明，面向产品、前端、后端、测试以及企业部署维护人员。代码、数据库迁移脚本和本文档发生不一致时，应先修复实现或补充迁移，再更新本文档；不要只通过修改文档掩盖行为差异。

当前产品形态为**单企业、本地部署**：每个企业独立部署一套前后端和一个 `brad_pms` 数据库，不在业务表中引入 `tenant_id`。未来如果演进为云端多租户，需要另行设计租户隔离、计费和跨租户运维，不能直接把本方案当作多租户实现。

## 2. 领域术语

| 术语 | 约定 |
| --- | --- |
| 企业 | 当前部署实例对应的一家公司，根组织为公司总部。 |
| 组织单元 | 组织树中的公司、BG、中心、部门、团队等节点，类型由 `sys_org_unit_type` 管理。 |
| 业务线 | 可承接项目的组织单元，通常是 BG 或其下级组织；选择时使用完整组织路径。 |
| 项目优先级 | 当前交付紧急程度，保存在 `project.priority`，分为低、中、高、紧急。 |
| 项目等级 | 项目重要性，保存在 `project.project_level`，分为战略（S）、关键（A）、重要（B）、常规（C）；新建项目默认常规（C）。它与优先级是两个独立维度。 |
| 主归属 | 人员当前唯一的主要组织关系，来自 `sys_user_position.is_primary = true` 的有效记录。 |
| 兼职/项目归属 | 人员除主归属外的一个或多个有效组织关系。 |
| 组织负责人 | `sys_org_unit.leader_user_id` 指向的负责人，与员工主归属是两套独立关系。 |
| 项目经理 | 项目级负责人，保存在 `project.project_manager_id`；未设置时前端显示“待分配”。 |
| 项目成员 | 项目协作范围内的人员，角色包括负责人、管理员、成员。 |
| 数据范围 | 角色在组织和项目数据上的可见范围，不等同于功能权限。 |
| 反馈工单 | 用户提交的可追踪问题、建议或咨询，具有状态、优先级、处理人和处理历史。 |
| 分诊 | 反馈进入“待初步处理”后，由具备 `feedback:manage` 的人员确认类型、优先级、负责人和处理路径。 |

用户展示遵循“中文名（英文名）”优先、邮箱兜底的规则，例如“张伟（Alex.Zhang）”。邮箱是新账号的唯一核心身份，登录时对邮箱执行 trim + 小写规范化并按 `email_normalized` 查询；中文名和英文名均可选。历史 `username` 字段保留为兼容字段，旧英文名登录在兼容期内仍可用，并继续以 `username_normalized` 保证唯一。

## 3. 核心业务不变量

以下规则必须由后端保证，前端只负责提供良好的编辑和错误提示体验：

1. 一个用户最多只能有一条**有效主归属**；设置新主归属时，旧主归属必须先失效或降为非主归属。
2. 用户可以拥有多条有效兼职/项目归属；归属关系有起止日期和状态，历史记录不可被前端静默覆盖。
3. 组织负责人独立于员工主归属。调整员工主归属不得自动改变组织负责人；调整组织负责人也不得改写员工主归属。
4. 组织树只能形成一棵无环父子树。停用组织前，必须处理有效子组织、成员和项目引用，不能产生孤儿数据。
5. 组织编码、岗位编码、角色编码、权限编码在各自命名空间内唯一；组织节点移动后必须同步维护 `path` 和下级节点可见范围。
6. `email_normalized` 使用 `Locale.ROOT` 小写规范化，并建立唯一索引；`Alex@Example.com`、`alex@example.com` 不能创建为两个账号。历史 `username_normalized` 同样保持唯一，避免旧客户端产生冲突。
7. 生产运行只使用 OceanBase；H2 仅用于自动化测试或一次性历史迁移快照，不能作为生产回退数据库。
8. 所有会改变人员、组织、角色、项目生命周期、导入结果或认证状态的写操作都要留下可追踪审计记录。
9. 已完成、已终止或已删除的项目/节点按只读处理；恢复项目必须通过明确的恢复操作和原因，不得靠普通编辑绕过生命周期。
10. 项目列表和项目详情必须读取同一套项目聚合字段：项目经理、业务线完整路径、负责人、状态、优先级、项目等级、周期和进度不能出现两套解释。
11. 反馈工单以 `client_request_id + reporter_id` 保证提交幂等；状态只能按允许的状态机流转，每次处理、分派、重开或关闭都必须追加历史并携带乐观锁版本。

## 4. 数据模型与关系

### 4.1 身份、组织和权限

```text
sys_user
  ├─< sys_user_position >─ sys_org_unit ─< sys_org_unit (parent_id/path)
  ├─< sys_user_role >─ sys_role ─< sys_role_permission >─ sys_permission
  │                         └─< sys_role_org_scope >─ sys_org_unit
  ├─< sys_auth_session
  ├─< sys_login_log
  └─< sys_operation_log (operator_id)

sys_org_unit
  └─< sys_org_unit_history (append-only before/after snapshots)
```

主要表职责：

| 表 | 职责 | 关键字段/约束 |
| --- | --- | --- |
| `sys_user` | 账号邮箱、可选中文名/英文名、认证状态 | `email_normalized` 唯一；`username_normalized` 为兼容字段且唯一；`ACTIVE/LOCKED/DISABLED/PENDING_ACTIVATION` |
| `sys_user_position` | 用户与组织的主归属、兼职归属、直属上级 | `user_id/org_unit_id/is_primary/assignment_type/status` |
| `sys_org_unit` | 可视化组织树和业务线 | `parent_id/path/type_id/leader_user_id/status` |
| `sys_org_unit_history` | 组织层级、负责人和状态的不可变变更记录 | `org_unit_id/action/before_json/after_json/operator_id/request_id/created_at`；只允许追加，不提供更新或删除接口 |
| `sys_position` | 岗位字典 | 编码唯一，可停用 |
| `sys_role` | 角色和数据范围类型 | 内置角色不可随意删除 |
| `sys_permission` | 细粒度功能权限点 | 以 `admin:*`、`project:*` 编码 |
| `sys_user_role` | 用户当前/历史角色授权 | 支持有效期和状态 |
| `sys_role_org_scope` | `CUSTOM_ORGS` 角色的组织范围 | 角色与组织多对多 |
| `sys_company_profile` | 企业名称、时区和安全策略 | 单实例一条企业配置 |
| `sys_operation_log` | 跨模块不可变操作审计 | `operator_id/action/resource_type/resource_id/project_id/before_json/after_json/reason/result/request_id/ip/user_agent/created_at`；只允许追加，按项目、操作人、动作和结果建立查询索引 |

### 4.2 项目协作

```text
project
  ├─< project_node
  │     └─< project_task
  ├─< project_member >─ sys_user
  ├─< project_follower >─ sys_user
  ├─< project_milestone
  ├─< project_comment >─ sys_user
  └─< project_lifecycle_log >─ sys_user (operator_id)
```

`project.org_unit_id` 是项目主业务线/主组织；`project_node.owner_id` 是节点负责人；`project_task.assignee_id` 是任务执行人。这三者不可混用。

需求澄清与范围基线节点在独立的节点工作台中维护纳入/不纳入范围项和需求清单；项目目标和节点交付结果沿用前一“项目立项与启动”节点，不在本节点重复维护。需求清单用于把已经澄清的内容拆成可追踪的需求条目，供后续方案、开发和验收引用；它不是任务看板，也不替代任务执行记录。每个需求条目包含稳定编号、名称、类型、优先级、验收标准和确认状态。只有需求状态为“已确认”的需求才能创建关联任务；任务完成状态不会自动确认需求，需求重新打开后已有任务保留但不能继续新增关联任务。节点只有在范围基线已确认、至少有一条纳入范围项、至少有一条需求且全部需求已确认时，才允许完成。

需求范围基线与节点一一对应：草稿可以由有节点编辑能力的责任人维护，编辑内容自动保存；满足完整条件后自动确认并锁定。如需修订，先重新打开；需求条目的确认状态仍由人工确认，不能由任务完成状态替代。基线带版本号，保存使用乐观锁，版本冲突返回 409，不会用旧页面覆盖他人的修改。重新打开会把现有需求条目恢复为待评审；保存时新增或内容发生变化的需求也会恢复为待评审，必须重新确认。已确认内容不会因普通页面刷新丢失，子项由服务端事务整体替换保存，接口仍受项目可读和节点生命周期约束。

方案设计、评审与决策节点在需求范围基线确认后维护一个方案包，不维护多个候选方案或任意评分。方案包只包含产品方案和技术方案；需求范围基线作为提交前的服务端前置条件，不在本节点重复展示。方案包字段自动保存，产品方案和技术方案都填写完整且上游基线已确认后自动提交方案包。方案包提交后必须完成三类固定评审：业务/产品评审、技术评审、测试/发布评审；每类评审各一条，可由节点负责人选择项目成员作为评审人。只有指定评审人或系统管理员可以完成对应评审。三类评审全部通过后，责任人填写决策结果（通过、条件通过或退回修改），决策字段自动保存；选择条件通过时还必须填写通过条件。方案包已提交、三类评审均已由指定评审人或管理员完成且决策填写完整后，系统自动确认决策并锁定方案包、评审和决策内容；若需修改必须先重新打开，方案包内容发生变化会使评审重新回到待完成。该节点只有在方案包已提交、三类评审全部通过且决策已确认时才能完成；保存使用乐观锁，版本冲突返回 409，所有写入仍受项目权限和节点生命周期约束。

业务验收与缺陷闭环节点只读取上一阶段已确认的需求编号、名称和验收标准，验收人员在本节点逐项记录验收结果和验证摘要，编辑内容自动保存。验收结论由业务人员人工确认，支持“通过”和“条件通过”；条件通过必须填写遗留事项。所有验收项通过且验收结论已确认后，节点才允许完成。关联缺陷在本页面只展示编号、标题、级别、处理状态和影响摘要，不提供关闭或修改缺陷状态的操作；缺陷的创建、处理和关闭由未来的缺陷管理模块负责，避免在验收页复制一套缺陷生命周期。验收草稿和结论使用乐观锁，确认/重新打开均写入操作审计。

计划、资源与风险基线、发布决策与运营交接、价值验证与项目复盘，以及开发测试与项目控制工作台的可编辑内容均采用自动保存；开发工作台中的专题和故事需要满足服务端的有效性校验后才会落库。自动保存不放宽项目权限、节点生命周期、字段校验、乐观锁或审计约束；节点完成与重新打开仍是独立的生命周期操作。

项目的 `priority` 表示当前紧急程度，沿用低/中/高/紧急；`project_level` 表示项目重要性，使用战略项目（S）、关键项目（A）、重要项目（B）、常规项目（C），默认值为常规项目（C）。调整项目等级属于项目资料修改，沿用 `project:write` 和项目生命周期边界，不改变项目经理、创建人或项目成员关系。等级评估参考投资规模、项目复杂度、战略重要性和项目收益；本系统当前只记录等级，不自动替代审批流程。

### 4.3 反馈中心

```text
feedback_ticket
  ├─< feedback_history
  ├─> sys_user (reporter_id)
  ├─> sys_user (assignee_id, nullable)
  ├─> project (project_id, nullable)
  ├─> project_task (task_id, nullable)
  └─> project_node (node_id, nullable)
```

| 表 | 职责 | 关键字段/约束 |
| --- | --- | --- |
| `feedback_ticket` | 当前反馈内容、上下文、状态、优先级、提交人和负责人 | `ticket_no` 唯一；`reporter_id + client_request_id` 幂等唯一（请求 ID 为空时不参与幂等）；`version` 乐观锁；软删除；上下文外键可为空 |
| `feedback_history` | 反馈创建、分诊、状态/优先级/负责人变更、重开和处理说明的追加式记录 | 只允许插入；保存前后状态/优先级/负责人、操作人、请求 ID 和时间；不得通过普通接口更新或删除 |

反馈上下文遵循“项目 → 任务/节点”的层级约束：任务和节点必须属于所选项目，节点与任务不一致时拒绝提交。反馈权限与项目/组织数据范围叠加：提交人只能读取自己提交的工单；具备 `feedback:manage` 的处理人员可按其授权范围查看和处理工单，只有全公司范围可读取全量工单；提交人始终保留自己的读取权。反馈权限族内部 `manage → write → read` 继承，其他权限族仍精确匹配。

## 5. 状态与生命周期

### 5.1 用户状态

| 状态 | 说明 | 允许的关键动作 |
| --- | --- | --- |
| `PENDING_ACTIVATION` | 已邀请、尚未设置密码 | 仅能通过激活流程完成首次登录 |
| `ACTIVE` | 可正常登录和访问授权数据 | 可改密码、刷新会话、参与项目 |
| `LOCKED` | 登录失败次数达到策略阈值 | 等待解锁或走管理员/重置密码流程 |
| `DISABLED` | 管理员停用 | 拒绝登录并撤销有效会话 |

### 5.2 项目、节点、任务和里程碑

| 对象 | 状态值 | 业务含义 |
| --- | --- | --- |
| 项目 | `ACTIVE` 进行中、`COMPLETED` 已完成、`TERMINATED` 已终止、`DELETED` 已删除 | 终止和恢复必须写入生命周期日志 |
| 节点 | `NOT_STARTED` 未开始、`IN_PROGRESS` 进行中、`COMPLETED` 已完成、`TERMINATED` 已终止 | 完成/回退/排期/负责人均走节点接口 |
| 任务 | `TODO` 待办、`DOING` 进行中、`DONE` 已完成 | 拖拽看板等同于状态变更，必须做项目权限校验 |
| 里程碑 | `PENDING` 未开始、`ACTIVE` 进行中、`COMPLETED` 已完成 | 里程碑与任务通过 `milestone_id` 关联 |

任务最多拆分一层，子任务与父任务归属同一项目节点。子任务截止日期是可选字段；没有截止日期的子任务不单独触发临期/逾期提醒。父任务通过普通更新或看板移动变为 `DONE` 时，后端在同一事务内将全部直接子任务设为 `DONE`，并只为原本没有截止日期的子任务补写父任务完成当天的 `Asia/Shanghai` 日期，已有日期不覆盖。父任务为 `DONE` 后，不能新增子任务，也不能把已有子任务直接回退到 `TODO` 或 `DOING`；需要返工时先回退父任务。子任务删除沿用任务删除权限和确认流程。

前端显示使用中文标签；接口和数据库使用稳定的英文枚举/整数编码。未知编码不得被静默映射成“已完成”，应保留原值并返回可诊断错误。

### 5.3 反馈工单

| 状态 | 中文显示 | 可流转到 | 说明 |
| --- | --- | --- | --- |
| `PENDING_TRIAGE` | 待初步处理 | `ASSIGNED`、`REJECTED`、`DUPLICATE`、`UNREPRODUCIBLE` | 新提交的默认状态，等待分诊 |
| `ASSIGNED` | 已分派 | `IN_PROGRESS`、`REJECTED`、`DUPLICATE`、`UNREPRODUCIBLE` | 已确定负责人 |
| `IN_PROGRESS` | 处理中 | `PENDING_CONFIRMATION`、`REJECTED`、`DUPLICATE`、`UNREPRODUCIBLE` | 负责人正在调查或修复 |
| `PENDING_CONFIRMATION` | 待确认 | `RESOLVED`、`IN_PROGRESS` | 等待提交人确认结果 |
| `RESOLVED` | 已解决 | `CLOSED`、`IN_PROGRESS` | 解决说明已填写，仍可重开 |
| `CLOSED` | 已关闭 | `IN_PROGRESS` | 完成归档，必要时可重开 |
| `REJECTED` / `DUPLICATE` / `UNREPRODUCIBLE` | 已拒绝 / 重复反馈 / 无法复现 | `IN_PROGRESS` | 异常结论必须填写处理说明 |

进入 `RESOLVED`、`CLOSED` 或异常结论状态时必须填写处理说明；进入 `ASSIGNED`/`IN_PROGRESS` 时必须指定有效的启用用户。所有状态变更都校验 `version`，冲突返回 409，前端需提示刷新后重试。

## 6. 权限与数据范围

### 6.1 功能权限

控制器通过 `@RequirePermission` 声明接口级权限：

| 权限编码 | 用途 |
| --- | --- |
| `project:read` | 查看项目及其全部协作内容；项目读取范围固定为全公司 |
| `project:create` | 创建项目；所有标准角色默认拥有，创建业务线仍受创建数据范围约束 |
| `project:write` | 常规修改项目资料、任务、节点和协作数据；不授予责任人之外的越权操作 |
| `project:manage` | 项目治理操作：成员/关注人、项目经理、终止、恢复、删除、任务和节点结构性调整 |
| `project:comment:write` | 发布项目评论；评论删除按作者本人或项目治理权限判断 |
| `admin:user:read` / `admin:user:write` | 人员、归属、角色分配和停用 |
| `admin:org:read` / `admin:org:write` | 组织树查看和编排 |
| `admin:role:read` / `admin:role:write` | 角色、权限点和数据范围 |
| `admin:import:write` | 组织与员工导入 |
| `admin:audit:read` | 审计日志查看 |
| `feedback:read` | 查看本人可见的反馈工单和处理历史 |
| `feedback:write` | 提交反馈、查看自己的工单并重开可重开状态的工单 |
| `feedback:manage` | 分诊、分派、调整优先级、填写处理说明和推进反馈状态 |

系统管理员（`system_role = 1`）拥有管理端绕过权限，但仍然必须经过认证、记录审计并遵守不可破坏的数据约束。普通管理员的能力来自实时角色授权，而不是前端隐藏菜单。

### 6.2 数据范围

角色数据范围支持：

- `ALL`：全公司范围。
- `SELF`：仅本人负责/创建/被分配的数据。
- `SELF_AND_SUBORDINATES`：本人及直属下属。
- `ORG`：本人主归属组织。
- `ORG_AND_DESCENDANTS`：本人组织及所有下级组织。
- `CUSTOM_ORGS`：角色绑定的指定组织集合。

数据范围由 `DataScopeResolver` 在服务端解析。范围解析失败、未知范围或组织已停用时，应采取最小权限原则；不能因为前端传入了组织 ID 就扩大访问范围。列表查询、详情查询、写入、删除和导出都必须使用同一套范围策略。

### 6.3 项目权限与数据范围统一规则

项目授权先判断功能权限，再判断数据范围和项目关系。`project:read` 是项目模块的读取门槛，只有“已登录且持有 `project:read`”的账号可以打开项目列表、详情、搜索、统计及项目下的任务、节点、里程碑、评论、附件、成员和关注人；项目读取范围固定覆盖全公司，不再按成员关系收窄。反馈工单继续使用独立的 `feedback:*` 权限，不能因为能看项目而读取反馈。

项目创建不要求在创建表单中填写项目经理。创建人自动成为项目责任人和项目成员；第一个节点确认时再单独选择项目经理。项目等级在创建时默认为常规项目（C），后续可在启动节点的项目基本信息中调整；项目经理一旦确认，与创建人拥有相同的项目级责任权限。创建请求中的业务线必须落在创建人的 `project:create` 数据范围内：`SELF` 对创建专指本人当前有效主归属组织，不包含下级组织；`ORG_AND_DESCENDANTS` 和 `ALL` 按常规组织范围解析。所有标准内置角色默认拥有 `project:create`。

写操作分为两条互斥的授权路径，不把所有条件机械地做成“功能权限 ∩ 数据范围 ∩ 责任关系”：

1. 治理路径：组织管理员和项目管理员等治理角色，依据对应的功能权限与数据范围操作范围内项目；`project_admin` 为全公司范围，`org_admin` 为本人组织及下级，部门负责人/业务线负责人第一期为本人组织及下级且不具备 `project:manage`。
2. 责任路径：项目创建人、项目经理可以管理该项目；节点负责人可以管理自己负责的节点；任务负责人可以有限修改自己负责的任务和上传该任务附件。责任人有限写入不强制要求 `project:write`，但不能改变负责人、节点归属、里程碑归属、删除任务或移动任务。普通员工默认没有 `project:write`，只能凭责任关系获得上述有限写入。

项目角色 × 项目权限矩阵如下（同一用户多角色取并集；系统管理员保留全局绕过）：

| 内置角色 | `project:read` | `project:create` | 常规 `project:write` | `project:manage` | `project:comment:write` |
| --- | --- | --- | --- | --- | --- |
| `member` | 全公司 | 本人主归属组织 | 无角色级常规写；本人任务/节点有限写 | 无角色级治理；本人责任项目按责任路径 | 全公司项目 |
| `project_manager` | 全公司 | 本人主归属组织 | 自己创建或担任项目经理的项目；其他项目按责任路径 | 仅自己创建或担任项目经理的项目 | 全公司项目 |
| `project_admin` | 全公司 | 全公司 | 全公司 | 全公司 | 全公司项目 |
| `org_admin` | 全公司 | 本人组织及下级 | 本人组织及下级 | 本人组织及下级 | 全公司项目 |
| `dept_manager` / `business_owner` | 全公司 | 本人组织及下级 | 本人组织及下级 | 第一期不授予角色级治理 | 全公司项目 |
| `system_role = 1` | 全局绕过 | 全局绕过 | 全局绕过 | 全局绕过 | 全局绕过 |

生命周期边界必须优先于能力矩阵：已删除项目对普通读取视为不存在，不出现在列表、搜索、统计或普通直链中；只有可管理的治理角色/责任人可以通过恢复入口加载并恢复。已终止项目可以读取全部历史内容，但不能编辑项目、节点、任务、附件或发布评论；只有恢复操作可写。已完成节点必须先回滚，已终止节点必须先恢复项目。项目 `ownerId`、组织卡片上的负责人、成员或关注关系都不是项目管理权的单独来源。

工作台仍然是个人工作集合，只展示本人待办、本人参与项目及相关动态，不因项目列表“全员可读”而变成全公司项目看板。搜索、统计、列表和详情的项目可见边界必须一致；全公司读取时搜索直接走数据库分页/关联条件，不先把全量项目 ID 装入内存。

成员、关注人、项目图片和任务附件的读取/写入都必须绑定具体项目或任务 ID；不能仅凭文件 key、用户 ID 或猜测 URL 绕过项目权限。管理端人员、组织和审计接口本期保持现有权限码和行为，不继承 `project:read`。前端能力字段只能控制交互，后端服务层校验才是最终边界。

### 6.4 通知中心与任务临期/逾期提醒

通知中心是现有 user_notification 站内通知的完整分页入口，不新建第二套消息系统。访问通知中心、顶部铃铛、未读数和标记已读接口都要求当前账号持有 project:read；在当前项目读取模型下，这意味着可以读取全公司未删除项目的全部项目内容。反馈工单仍使用自己的 feedback:* 权限，不因项目可读而继承反馈可见性。

通知中心提供“全部、未读、临期、逾期”四种互斥视图。临期和逾期筛选分别对应 TASK_DUE_SOON、TASK_OVERDUE；type 传入其他值返回 400。筛选变化由前端回到第 1 页，翻页保留筛选。顶部铃铛继续保留最近 20 条预览，并提供“查看全部”进入 /notifications；提醒较多时可以挤占较早事件，完整结果以通知中心分页为准。

任务提醒第一期只写入站内通知，不调用会发布出站 Webhook 的 emit/事件通知入口，也不发送邮件、飞书或企业微信。作业默认关闭，配置如下：

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| pms.notification.task-reminder.enabled | false | 权限收口完成、通知 SQL 可读性过滤验收通过后才允许显式开启 |
| pms.notification.task-reminder.cron | 0 0 9 * * * | 每天 09:00 扫描 |
| pms.notification.task-reminder.zone | Asia/Shanghai | 用于计算当地日期和调度时区 |
| pms.notification.task-reminder.due-soon-days | 7 | 允许 1–30；默认临期窗口覆盖今天至 today + 7，共 8 个自然日 |

状态窗口和通知写入条件必须分开理解：

1. 临期状态窗口为 dueDate ∈ [today, today + N]，默认 N=7；临期通知只在任务进入窗口的外沿当天、即 dueDate = today + N 的 09:00 写入一次。到期当天不发临期，也不会在窗口内每天重复。
2. 逾期通知只在 dueDate = today - 1 的 09:00 写入一次。同一任务每个企业当地日最多一条逾期通知；更早的历史逾期不补发。
3. 上线第一天也只按当天两个边界扫描：当天进入临期窗口的任务和当天刚逾期的任务。任务已经在窗口内、已经历史逾期，或作业停机错过边界日，都不回填、不停机补发。
4. 新建、改期或重开任务只有在当天恰好落在上述边界时才可能写入提醒；改到窗口内部、改成今天或改到窗口内其他日期不补发。重开同理。
5. 只通知任务当前 assigneeId；没有负责人、任务已完成、负责人已停用/逻辑删除、任务已删除或项目已删除/非可运行状态的候选不会生成新提醒。更换负责人不撤回旧提醒、不改旧提醒的已读状态；后续符合条件的扫描只面向新负责人。

提醒去重由 V15 的 dedupe_key 和唯一索引保证：

- 临期键为 TASK_DUE_SOON:taskId:dueDate；
- 逾期键为 TASK_OVERDUE:taskId:today，today 是企业配置时区的当地日期，不是 dueDate；
- 同一用户、类型和去重键只能有一条记录。历史普通通知的 dedupe_key 保持 NULL；第一期提醒只标记已读，不软删除提醒记录，避免软删后复用唯一键。

通知的可见性和分页必须在 SQL 中完成后再分页或计数：通知属于当前用户、通知记录未删除，且 project_id 为空或其项目仍存在、未删除且状态不是 DELETED。当前 project:read 已固定为全公司读取，因此“当前用户不可读”在本期等价于不具备 project:read 的接口请求被拒绝；不能先 LIMIT 80 再由 Java 丢弃不可见项目。通知列表、顶部预览、/notifications/page 和未读数必须使用同一删除/状态过滤边界。项目终止仍可读，历史通知可以打开但不再生成新提醒；项目删除按不存在处理，不出现在列表、未读数或普通深链中，也不通过 403 暴露其存在。

提醒服务记录当地扫描日期、扫描结果和写入数量，不能记录密码、令牌、Webhook secret 或通知去重键以外的敏感信息。通知标题和正文按纯文本展示，不使用 v-html。作业日期使用配置的 zone；工作台 dueSoon 本期仍按 JVM 默认时区计算，宿主机不是 Asia/Shanghai 时，午夜附近工作台数字可能与通知日期相差一天，这是已知差异，不由通知作业偷偷修改工作台。

## 7. 认证与安全规则

1. 登录接口以邮箱为核心，服务端先执行 trim + 小写规范化再查询；旧英文名仅作为兼容字段；错误提示不能泄露“账号不存在”还是“密码错误”的可枚举信息。
2. 成功登录签发访问令牌和刷新令牌；刷新令牌只存哈希，退出登录或停用账号时撤销会话。
3. 连续失败登录会累加 `failed_login_count`，达到策略后进入 `LOCKED`；成功登录会重置失败计数并记录 `last_login_at`。
4. 密码重置令牌只存哈希并设置有效期，默认不在生产响应中暴露明文令牌。
5. JWT 密钥必须通过 `PMS_JWT_SECRET` 注入，生产随机强度至少 32 字节；账号密码、令牌和数据库密码不能写入日志或提交到仓库。
6. CORS 只允许显式配置的前端来源；健康检查 `/api/health`、`/api/healthz` 可匿名访问，其余接口默认需要 `Authorization: Bearer <token>`。
7. 认证失败返回 401，权限不足返回 403，参数错误返回 400，业务异常返回可读的错误信息和 `requestId`；前端不得把 500 当作“无数据”。

## 8. API 约定

### 8.1 返回与分页

接口统一使用 `ResponseResult` 包装；分页使用 `PageResult`，请求参数沿用 `currPage` 和 `pageSize`。页码最小为 1，人员分页大小限制为 1–100，其他分页接口也应设置合理上限，避免无界查询。

### 8.2 接口分组

| 领域 | 主要接口 |
| --- | --- |
| 认证 | `POST /auth/login`、`/auth/refresh`、`/auth/logout`、密码修改/激活/重置、`GET /auth/me` |
| 项目 | `POST /projects/page`、项目 CRUD、`/terminate`、`/restore`、统计 |
| 节点与任务 | `/projects/{projectId}/nodes`、`/projects/{projectId}/tasks`、`/tasks/{id}/move` |
| 方案设计评审决策 | `/projects/{projectId}/nodes/{nodeId}/solution-design` 及其 `submit`、`reviews/{reviewType}/complete`、`decision/confirm`、`decision/reopen` |
| 协作 | 成员、关注人、里程碑、评论接口 |
| 组织 | `GET /org/tree`（项目选择器）、`/admin/org/tree` 及组织 CRUD/移动 |
| 人员 | `/admin/users` 分页、邀请、主归属、兼职归属、角色、停用 |
| 角色 | `/admin/roles` CRUD 和权限/数据范围 |
| 导入 | 组织/用户预览、提交、CSV 模板、错误报告下载 |
| 审计 | `GET /admin/audit`、`GET /admin/audit/{id}`，按动作、资源、项目、人员、结果、请求 ID、时间和分页筛选 |
| 反馈 | `POST /feedback/tickets`、`GET /feedback/tickets`、`GET /feedback/tickets/assignees`、`GET /feedback/tickets/{id}`、`PATCH /feedback/tickets/{id}`、`POST /feedback/tickets/{id}/reopen` |

写接口应做到幂等或明确返回冲突；删除、停用、终止等危险动作必须在服务端再次校验当前状态和权限。

## 9. Excel/CSV 导入规范

导入是“预览 → 校验 → 提交”的两阶段流程：

1. 管理员上传 Excel/CSV，服务端限制文件类型、大小（当前实现上限 5 MB）和行数（当前实现上限 5000 行）。
2. 预览阶段只解析和校验，不写业务表；返回逐行错误、规范化结果和汇总数量。
3. 组织导入先处理父子关系和编码冲突；员工导入要求邮箱和主组织编码，中文名/英文名可选，直属上级优先填写邮箱（兼容旧英文名），同时校验角色和日期。
4. 提交阶段使用导入任务 ID，在事务内写入组织、用户、归属和角色，并写入 `sys_import_job` 与操作日志；失败应整体回滚，不产生半批数据。
5. 同一规范化邮箱、组织编码或角色编码重复时必须明确报错；英文名如填写也必须唯一；已存在记录只能按产品定义的更新策略处理，不能静默覆盖。
6. 导入完成后可在审计日志中通过 `IMPORT_COMMITTED` 和导入任务 ID 追踪；预览结果过期后不可再次提交。
7. 提交接口以导入任务 ID 做幂等键：同一任务已成功时返回成功结果，不重复写入；任务状态与请求冲突时拒绝提交。失败任务记录原因和时间，可通过 `/admin/import/{jobId}/errors.csv` 下载服务端保存的逐行错误。

- OceanBase profile 运行时不依赖 Flyway 自动执行；升级前先执行预检、备份策略和迁移脚本，再启动应用。
- `application-h2.yml` 和 H2 快照只服务自动化测试/一次性迁移工具；文档、示例和上线脚本不得引导用户用 H2 运行生产。
- 启动后通过 `/api/health` 或 `/api/healthz` 验证应用与数据库连通性；连接失败时优先检查网络、租户、账号权限和字符集，不要切换到 H2 掩盖故障。

## 11. 审计、可观测性与测试

方案设计节点的规则摘要：决策确认后锁定；如需修改，先重新打开决策。

所有关键变更至少记录：操作人、动作、资源类型、资源 ID、项目 ID（项目域事件）、变更前后白名单摘要、结果、原因（适用时）、请求 ID、IP、User-Agent 和 UTC 时间。项目、节点、任务、成员、关注人、评论、附件、图片、角色、数据范围、人员归属、组织、导入、认证和保留清理均按动作目录写入 `sys_operation_log`；普通 GET 不写审计。成功业务变更与成功审计在同一事务内提交，审计插入失败时业务变更回滚。

审计动作使用稳定英文编码，前端只负责本地化展示。项目域至少包括 `PROJECT_CREATED`、`PROJECT_UPDATED`、`PROJECT_MANAGER_CHANGED`、`PROJECT_TERMINATED`、`PROJECT_RESTORED`、`PROJECT_DELETED`、节点/任务及协作资源变更动作；权限域至少包括 `ROLE_PERMISSION_CHANGED`、`ROLE_SCOPE_CHANGED`、`USER_ROLE_ASSIGNED`、`USER_ROLE_UNASSIGNED`、`USER_PRIMARY_POSITION_CHANGED`、`USER_DISABLED`。角色权限和数据范围变化必须分别能从 before/after 摘要辨认，不能只留一条无意义的“角色已更新”。

审计接口只要求 `admin:audit:read`，不因 `project:read` 自动开放，也不再按项目读取范围过滤；有权限的审计人员可查询全量操作记录。详情页显示字段级差异和项目/操作人展示名；项目或人员已删除时保留 ID 并显示未知/已删除，不回写历史。密码、JWT、刷新/重置令牌、令牌哈希、密钥、评论/反馈正文、来源 URL、幂等键、请求体和二进制内容禁止进入 before/after。默认保留 180 天，按 UTC 每批最多清理 500 条，并用 `AUDIT_RETENTION_RUN` 记录候选数、删除数、保留天数和 dry-run 状态。

每个请求可通过 `X-Request-Id` 关联前后端日志。发布前至少执行：

- `mvn test`：认证、权限、数据范围、组织、导入、控制器和配置测试。
- 迁移脚本在目标 OceanBase 实例上执行并验证表、索引、种子角色和健康检查。
- 对匿名访问、401/403、主归属唯一性、组织负责人独立关系、项目列表/详情一致性进行验收。
- 检查日志不包含密码、JWT、刷新令牌、重置令牌和数据库连接密码。
- 反馈中心至少验收：普通用户只能看到自己的工单；处理人员可按授权范围分诊且候选负责人不越界；重复 `clientRequestId` 不重复建单；非法状态流转、版本冲突和越权上下文均被拒绝；关闭时间和重开说明符合生命周期规则；审计不包含正文、来源 URL、幂等键或处理说明原文，历史记录完整可追溯。

## 12. 变更规则

新增业务字段先补充领域模型和迁移脚本，再实现服务和接口；删除或重命名字段必须提供兼容期或数据迁移。新增权限点必须同时更新角色种子、后端 `PermissionCode`、前端路由守卫和本文件的权限表。任何影响主归属、组织负责人、数据范围、项目经理或导入行为的修改，都必须补充对应测试和审计说明。
